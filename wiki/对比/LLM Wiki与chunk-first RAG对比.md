# LLM Wiki 与 chunk-first RAG 对比

## 一句话结论

**LLM Wiki 维护一个持久的综合工件；chunk-first RAG 每次查询都从原始文档重新检索、重新综合。** 前者让知识复利，后者不累积。

## 对比表

| 维度 | chunk-first RAG | LLM Wiki |
|---|---|---|
| **状态** | 每次查询重新检索原始 chunk | 维护一个持久综合工件 |
| **交叉引用** | 查询时临时拼接 | 已预先建好 |
| **矛盾标记** | 不标记 | 已预先标记（`> [!contradiction]`） |
| **知识是否累积** | 否（同一问题重复做功） | 是（知识像利息一样复合增长） |
| **单次摄入成本** | 低（存文件 + 建向量索引） | 高（一次触碰 10–15 个页面） |
| **单次查询速度** | 依赖检索质量 | 更快（索引 + 已综合页面） |
| **适用规模** | 百万级 tokens、语料高频变化 | 约 50K–100K tokens 以内 |
| **数据归属** | 常落在服务商系统内 | 本地 markdown，文件优于应用 |

## 典型场景选型

| 场景 | 更优选择 |
|---|---|
| 个人知识库、第二大脳 | **LLM Wiki** |
| 小团队共享研究上下文 | **LLM Wiki** |
| 语料每小时变化的大规模检索 | **RAG** |
| 需要显式、可导航、无隐藏 embedding 的知识产物 | **LLM Wiki** |

## LLM Wiki 的代价

- **摄入更重**：一份来源需要更新多个页面
- **schema 必须持续维护**：`WIKI.md` / `CLAUDE.md` 需要人和 AI 共同演进
- **lint 不可省**：漏掉矛盾会逐层累积

## 辨认特征

判断一个系统属于哪一类，看三点：

1. 问同一个问题两次，是否**做两遍功**？——是则偏 RAG
2. 交叉引用是**预先存在**还是**查询时拼**？
3. 好的回答是否有**归宿**（写回知识库）？——无归宿则不产生复利

## 对本项目/学习的价值

- **AI 测试迁移点**：这组差异可映射为 AI 产品评测的指标设计问题——**评测对象究竟是「检索结果」还是「维护后的知识产物」**。
- 本 vault 属 LLM Wiki 一侧，其「问答归档」环节（本页同批建立）正是复利机制的关键实现。
