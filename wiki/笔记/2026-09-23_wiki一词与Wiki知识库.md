## 核心发现一：vault 路径 ≠ 工作区路径

**这是本轮最重要的一条。** 我最初按工作区 `D:\AI\Hermes\learn` 推理，以为 vault 根就是它——但 `learn` 下**根本没有 `wiki/` 目录**。

真实 vault 根是 **`D:\AI\Hermes\claude-obsidian`**，由 `%APPDATA%\obsidian\obsidian.json` 注册（`open: true`）。

> **教训**：涉及本地资源路径时，**先核实再动手**。obsidian.json 是权威来源，不要靠目录名推断。

另外：vault 有自己的 `.workbuddy/memory`（标题「项目长期记忆 — claude-obsidian vault」），与 `learn` 的**彼此独立**，勿混用、勿代写。

## 核心发现二：`.raw/` 引用不能用 wikilink

首次写入时我在 frontmatter 用了 `sources: - "[[.raw/claude-obsidian-ecosystem-research.md]]"`，链接校验报 broken。排查后确认两个坑：

1. **`[[path]]` 是 git pathspec 语法**——`.raw/x.md` 的 wikilink 会让 git 把 `[[.raw/x.md]]` 当成 pathspec，出现 `ambiguous argument`。更严重的是，`git add -- .raw/笔记/X.md` 会因 `.raw/笔记/` 下存在字面 `[[...]]` 内容而**报 pathspec 歧义**。
2. **`.raw/` 裸路径也不解析**——`.raw/x` 不带 `.md` 时脚本只对 `.md` 结尾做文件存在性判断，仍报 broken。

**全库既有约定是只用 frontmatter 纯字符串**（`source: ".raw/..."`，不带双括号）。本次已全部改为该写法。

## 核心发现三：`.raw/笔记/X.md` 应按 1:1 映射到 `wiki/笔记/X.md`

归档后跑 `check_raw_updates.py`，我的新源落在「未映射」，而**同目录的旧文件却没有**。查脚本 `find_wiki()` 第 74–77 行才发现：

```python
# 4. Direct same-path mapping (Codex/, 笔记/)
wiki_path = os.path.join(WIKI, raw_rel.replace(ext, '.md'))
if os.path.isfile(wiki_path):
    return wiki_path
```

即 `.raw/笔记/` 与 `Codex/` 走**同路径直接映射**。我当初只建了 `wiki/问答/` 归档，缺了 `wiki/笔记/` 同名页 → 被脚本判为未映射（**静默，不报错**）。本页即为补齐该约定而建。

> **教训**：`.raw/` 下每个内容文件都应有对应的 `wiki/` 页面，路径可预测；「问答归档」是额外的第 4 类产物，不能替代笔记页。

## 核心发现四：校验脚本的两个使用陷阱

`scripts/wiki-linkcheck.py` 自身没问题，但用法有坑：

| 陷阱 | 现象 | 正确做法 |
|---|---|---|
| **路径必须含 `wiki/` 前缀** | `file 实体/_index.md` 报 1 断链；`file index.md` 误报 **66 断链 / 91 歧义** | 一律传完整 vault 相对路径，如 `wiki/实体/_index.md` |
| **表格内 `\|` 会被误报** | `[[wiki/index\|别名]]` 在表格里被判 broken 4 处 | 表格内 `\|` **必需**（否则表格列错乱），误报可接受；正文里才该用单管道 |

**如何区分「我引入的断链」与「既有断链」**：用 `git show HEAD:<file>` 取改动前版本，与本文件做「无法解析链接集合」的差集。本次结论：**新引入断链 0，并顺带修复了 `dashboard.md` 的 5 处既有断链**（原写法缺 `wiki/` 前缀）。

### 已知误报（本页 5 处，非真实断链）

`wiki-linkcheck.py` 的 `LINK_RE = re.compile(r"\[\[([^\]]+)\]\]")` 是**简单正则，不剥离代码块与行内代码**，因此本页讲解语法时出现的示例会被判为断链：

| 位置 | 内容 | 为何必须这样写 |
|---|---|---|
| `find_wiki()` 代码块 | `[[path]]` | 这是 **git pathspec 的字面语法**，改成别的形式就不准确 |
| frontmatter 反例 | `[[.raw/claude-obsidian-ecosystem-research.md]]` | 记录我实际犯过的错误写法 |
| 说明文字 | `[[.raw/x.md]]`、`[[...]]`、`[[wiki/index\|...]]` | 同上，均为语法示例 |

> **结论**：有断链标注 ≠ 真有断链。**必须看明细**（`grep "X "`）确认是否落在代码块内。这与「表格内 `\|` 会被误报」属同一类**工具局限**，处理原则一致——**不为迁就工具而牺牲内容准确性，但要在页内标注清楚**。

## 可复用的归档流程（7 步）

1. 读 `wiki/hot.md` → `wiki/index.md`，掌握当前上下文（勿跳过热缓存直接扫全库）
2. 在 `.raw/` 建原始记录页（只读源）
3. 建/更新四类知识页：**概念页、来源摘要页、对比页、实体页**
4. 建 `wiki/问答/` 归档问答（Karpathy 模式的复利环）
5. 建 `wiki/笔记/` 同路径页（满足 `check_raw_updates.py` 的直接映射约定）
6. 更新 `wiki/index.md`（主题板块 + AUTO-CATALOG）、各子 `_index.md`、`hot.md`（**全量覆盖**）、`log.md`（**新条目置顶**）、`元数据/dashboard.md`
7. 跑 `wiki-linkcheck.py file <完整路径>` 逐文件校验；用 `git show HEAD:<file>` 差集确认**新引入断链为 0**；跑 `check_raw_updates.py` 确认**待更新 0**

## 闭环意义

Karpathy LLM Wiki 模式中「`query` 之后把好答案写回 wiki 形成复利」这一环，此前一直空转——`wiki/问答/` 自 2026-07-01 创建以来始终为「暂无已归档的问答」。**本次首次跑通**，`hot.md` / `log.md` / `index.md` 三处均已记录该里程碑。

这正好呼应了 vault 里那句：

> **wiki 才是产品。聊天只是界面。**

聊天中的知识若不归档，就只是一次性的；写回 wiki 后才开始复利。
