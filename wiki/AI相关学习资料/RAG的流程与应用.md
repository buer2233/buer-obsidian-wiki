# RAG 的流程与应用：六层工程链路与检索内核

> **一句话定义**：RAG = 把「知识」从模型权重（参数化记忆）搬到可秒级替换的外部索引（非参数化记忆），按「**价值层 → 数据层 → 向量层 → 存储层 → 内核层 → 实战层**」六层递进搭建的一条工程链路——**绝大多数线上故障不是「模型不行」，而是「资料没整理好」或「货架选错了」**。

**适用定位**：写给有测试开发背景、正转向 AI 测试的工程师。已有资料（`10_RAG测试必背学习资料`、`大模型必学基础知识` 第 7 章）已覆盖「RAG 测试方法论与评测指标」，**本篇不重复方法论，只补工程实现链路**：RAG 到底怎么搭起来、每一层会坏在哪。每一节按 **概念 → 要点 → 测试视角** 展开。

> [!key-insight] 贯穿全文的一条判断
> **RAG 的测试工程师，80% 的定位工作发生在第 2、3、4 层（数据/向量/存储），而不是第 1 层。** 因为模型层的问题一眼可见，而这三层的缺陷是**静默的**——不报错，只是越来越不准。

## 第 0 章 学习地图：为什么按数据流动方向排

| 层 | 章节 | 对应问题 | 典型故障归属 |
|---|---|---|---|
| **1 价值层** | 第 1 章 | 它为什么必需、往哪走 | 架构选型错误（该用 RAG 却去微调） |
| **2 数据层** | 第 2 章 | 喂什么进去、粒度多细 | 切分不当、上下文丢失/截断、脏数据 |
| **3 向量层** | 第 3 章 | 文字怎么变成可比的距离 | 模型不一致、度量与归一化不匹配 |
| **4 存储层** | 第 4 章 | 向量存哪、怎么查 | 选型错、无持久化/权限过滤、幽灵索引 |
| **5 内核层** | 第 5 章 | 凭什么快、凭什么只对 95% | 把 ANN 的「近似」当成 bug 或当成正常 |
| **6 实战层** | 第 6 章 | 拿它做成什么 | 混合检索无收益、脱敏不彻底、越权 |

## 一、价值层：RAG 为什么必需（第 1 章）

**LLM 是参数化记忆系统**，训练完成即冻结——推理能力很强，但「知道什么」被锁死在知识截止日。RAG 的实质不是「让模型记住更多」，而是**「把记忆的职责从权重转移到索引」**。

| 缺口 | 商业后果 | RAG 能否解决 |
|---|---|---|
| 知识截止 | 内部制度、新政策答不上 | ✅ 根本解决——索引随时更新 |
| 不可溯源 | 无法审计、无法建立信任 | ✅ 根本解决——可强制输出引用 |
| 私有数据不可用 | 通用模型对内部业务零认知 | ✅ 根本解决——数据不出内网 |
| 幻觉 | 企业场景产生合规风险 | 🟡 显著缓解，不是消除 |
| 领域专业度不足 | 垂直问答错答率高 | 🟡 部分解决——取决于知识库质量 |

**RAG vs 微调**——判断依据只有一条：**你要改的是模型「怎么表达」，还是模型「知道什么」？** 微调**无法可靠注入新知识**，它擅长的是输出风格与格式。业界结论是 **All of the above**（RAG 管事实，微调管风格）。

### 三阶段数据流：离线 / 在线必须分开看

| 阶段 | 时机 | 核心决策 | 这一层坏了会怎样 | 关键指标 |
|---|---|---|---|---|
| **Indexing** 索引 | **离线**，只跑一次/增量 | 切分粒度、Embedding 模型、索引类型 | 检索到的内容整体不对，需重建索引 | 索引覆盖率、切分完整率 |
| **Retrieval** 检索 | **在线**，每次请求 | 度量、Top-K、是否重排 | 该找到的没找到 / 找到了但排后面 | Hit Rate@K、Recall@K、MRR |
| **Generation** 生成 | **在线**，每次请求 | Prompt 约束、上下文拼装与长度 | 资料给对了但答案还是错 | Faithfulness、Answer Relevancy |

> [!key-insight] 面试高频：答案错了，是检索还是生成的问题？
> **按链路顺序二分**：先看 Top-K 里有没有「应当回答问题的那份文档」——**没有 → 检索问题**（查切分 / Embedding 一致性 / 查询改写 / 元数据过滤 / ANN 参数）；**有但答案仍错 → 生成问题**（查 Prompt 约束 / 上下文拼装 / 是否被截断 / K 过大）。
> 这是「错题 #020」的核心考点。另外，**检索得分高 ≠ 对生成有帮助**——「看起来很相关」的文档可能把模型带偏，这正是检索后必须加 **Rerank** 的原因。

### 三代范式与生态全景

| 范式 | 新增环节 | 解决的问题 |
|---|---|---|
| **Naive RAG** | 无（检索→拼接→生成） | 让模型能「看到」外部资料 |
| **Advanced RAG** | **Pre-Retrieval**（改写/扩展/路由）+ **Post-Retrieval**（重排/压缩/融合） | 原始 Query 检索不准、召回内容太杂 |
| **Modular RAG** | Routing / Memory / Fusion / Predict / Demonstrate 等可插拔模块 | 架构适配不同任务，而非一条流水线走到底 |

## 二、数据层：文档加载、分块与元数据（第 2 章）

**加载**：RAG 效果不好的第一原因不是模型不够强，而是文档处理得不够好——把异构源统一成 `Document = {content, metadata}`。常见陷阱：扫描件 PDF 其实无文本层（直接解析得空串，**必须先判断再走 OCR**）；HTML 不去噪会把全站菜单当正文入库，严重稀释检索质量。**清洗四件事**：去噪（页眉页脚页码）、规范化（全半角/空白）、**脱敏（医疗/HR 合规红线）**、去重。

> [!key-insight] 为什么必须去重？
> 重复内容会**同时占据 Top-K 的多个槽位**——同一文档存 3 份，Top-5 可能被它占掉 3 个名额，真实有效的候选被挤出。这是「召回率看起来不低、可用信息却很少」的典型原因。

### 分块（Chunking）：RAG 最关键的参数决策

| 策略 | 优势 | 局限 | 适用 |
|---|---|---|---|
| 固定长度切分 | 实现最简 | ⚠️ 会在句子中间切断 | 仅快速验证 |
| **递归切分** | **保留语义边界，官方推荐首选** | 仍可能切断超长单段 | 绝大多数场景默认 |
| 结构感知切分 | 与文档逻辑结构对齐 | 依赖文档结构良好 | 技术文档、法规、代码 |
| 语义切分 | 切点最贴合语义边界 | 成本高、不稳定 | 质量要求极高 |
| 父子分块 / 句子窗口 | 兼顾检索精度与上下文完整 | 需维护两级索引 | 长文档问答 |

![文档分块解耦策略（LlamaIndex 官方）](../../_attachments/images/AI相关学习资料/RAG的流程与应用/07-文档分块解耦策略-llamaindex官方.png)

*图 7：把「用于检索的粒度」与「用于生成的粒度」解耦——检索用语义浓缩版（摘要 / 单句），生成用完整原文（原文块 / 扩展窗口）。*

| 参数 | 经验范围 | 调大 | 调小 |
|---|---|---|---|
| **chunk_size** | 200–500 Token（中文 300–800 字符） | 语义稀释、噪声多、Token 成本升 | 语义断裂、答案跨块被切碎 |
| **chunk_overlap** | **chunk_size 的 10%–20%** | 索引膨胀；超 30% 收益递减 | ⚠️ **答案跨边界时两块都被切断** |

> [!gap] 这是「错题 #020」的直接失分点
> 「上下文丢失/截断」的根因就是 **chunk_size 过大导致关键信息被切在两块之间，或 overlap 缺失导致边界两边都不完整**。结论：**overlap 不是可选项，是必需项**——因为没有任何切分策略能保证语义永不跨边界。Test 用例：把答案句故意构造在切分边界上，断言**至少有一个 chunk 完整包含它**。

**中文分块的特殊处理（易忽略）**：LangChain 默认分隔符 `["\n\n","\n"," ",""]` 是为英文（有空格分词）设计的，**中文无词间空格，直接用默认配置会把句子从中间切断**。解法是自定义分隔符列表并加入中文标点（`。`、`，`、`、`、全角句号等）。

### 元数据与结构化检索：给语义搜索加上精确约束

向量检索不理解精确标识符，也不理解业务权限。元数据的四个用途：**权限控制**（`tenant_id`/`dept`/`acl`）、**版本时效**（`version`/`effective_date`）、**溯源引用**（`source`/`page`/`section`）、**检索增强**（`doc_type`/`keywords`）。

| 方式 | 执行时机 | 安全性 | 检索质量 |
|---|---|---|---|
| **预过滤 Pre-filter** | 相似度计算**之前**缩小候选集 | ✅ 安全 | 过滤过严可能漏召回 |
| **后过滤 Post-filter** | 先取 Top-K 再筛 | ❌ **有泄露风险** | Top-K 被无效结果占满 |
| 过滤中 In-filter | ANN 图遍历过程中应用约束 | ✅ 安全 | 兼顾安全与召回 |

> [!key-insight] 企业 RAG 的安全底线（必背）
> **权限过滤必须在检索之前完成（Pre-filter）**。原因：后过滤意味着无权限内容**已经进入模型上下文**，即使最终没输出，也存在被间接泄露的风险（如通过摘要或推理暴露）。**语义相似度不是访问控制机制**——这句话的工程含义就是「权限必须前置」。

![元数据过滤与结构化检索（LlamaIndex 官方）](../../_attachments/images/AI相关学习资料/RAG的流程与应用/08-元数据过滤与结构化检索-llamaindex官方.png)

*图 8：上为预过滤（自动推导元数据过滤条件后只检索命中节点）；下为文档层级 + 递归检索（摘要定位 → 原文取用）。*

**测试视角（数据层）**：这是**最适合自动化回归**的环节（输入输出确定性）。关键维度——格式覆盖（空字符串是最常见的静默失败）、扫描件识别（不得静默入库空内容）、**脱敏完整性（正则反向扫描，断言零命中）**、去重有效性、元数据完整性（`source`/`version` 非空率 100%，缺失即等于无法溯源 + 越权风险）。分块则最适合**参数化测试**：答案边界完整性、块长分布、块数膨胀率、元数据继承。

## 三、向量层：Embedding、相似度与 Top-K（第 3 章）

**Embedding 把「语义相似」转换成「空间距离」**，检索随之退化为纯数学问题：在向量库中找最近的 K 个。

![向量空间语义聚类二维示意（Weaviate 官方）](../../_attachments/images/AI相关学习资料/RAG的流程与应用/09-向量空间语义聚类二维示意-weaviate官方.png)

*图 9：语义相近的对象在向量空间中聚集成团，因此检索才能退化成「找最近的 K 个点」这个纯几何问题。*

**四个工程属性**：维度（384/768/1024/1536/3072，建索引时就必须确定）、**是否归一化（决定用内积还是余弦）**、模型一致性（**同一索引必须用同一模型**）、语言与领域适配（中文场景必须选中文优化模型）。

| 路线 | 代表 | 劣势 | 适用 |
|---|---|---|---|
| API 集成 | OpenAI `text-embedding-3` | ⚠️ **数据出网（合规红线）** | 公开数据、快速原型 |
| **本地部署** | Ollama + `nomic-embed-text`、BGE | 需算力与运维 | **企业内部数据** |

**三种相似度度量的关键数学关系（面试必问）**：若 A、B 均已 L2 归一化，则 `cos(A,B) = A·B`，且 `‖A−B‖² = 2(1−cos)`。

> [!key-insight] 「余弦相似度和欧氏距离结果是不是一样？」
> **当且仅当向量已归一化时两者排序一致**（`‖A-B‖² = 2(1-cos)` 单调递减）；**未归一化时不一致**——欧氏距离会被向量长度影响而误判。所以「模型是否输出归一化向量」这个前提，直接决定了答案。决策规则：已归一化 → 用**内积**（最快，等价余弦）；不确定 → 用**余弦**（最稳妥）。

**Top-K 的权衡三角**：太小（K=1–2）漏召回；适中（K=3–5）是默认区间；太大（K=20+）触发 **Lost in the Middle**——模型对上下文中间位置信息的利用效率显著低于首尾，「把 K 调大提升召回」往往**不能提升最终答案质量**。正确做法是用 Rerank 提升 Top-1 命中率。
**确定 K 的三步法**：① Recall@K 曲线找饱和点（增量 < 2%）；② Context Precision@K 找噪声拐点；③ 取交集并叠加 Token 成本与 P95 延迟约束。

**查询优化手段**：查询改写、多路召回（Multi-query）、**HyDE**（先假设答案再检索）、查询路由、元数据约束、**混合检索（Hybrid）**。

**测试视角（向量层）**：缺陷往往是**静默的**。最高优先项是**模型一致性**——索引元数据记录 `embedding_model` + `dim`，在线查询时校验，**不一致必须报错而非静默降级**（换模型没重建索引会让检索整体劣化却不报错）。其余：维度一致性、归一化状态、语义保持性（同义对相似度 > 0.8 且 > 无关对）、确定性（同文本三次调用结果一致）、截断行为（超长输入必须明确截断或报错，**不得静默返回前半段的向量**）、中文适配。度量层则要断言「已归一化时 COSINE 与 IP 排序完全一致」。

> [!gap] 阈值不能拍脑袋定
> 阈值必须基于「同义对得分分布」与「无关对得分分布」的**可分离性**来确定：先算一批标注数据的得分分布，找出两类分布的分界点，再据此设阈值——比直接抄一个「0.8」可靠得多。

## 四、存储层：向量数据库选型（第 4 章）

向量数据库索引的是「语义空间中的位置」而非「字段值」。**五项核心能力**：向量索引（ANN）、元数据过滤、相似度度量、CRUD 与增量更新、持久化与扩展。

> [!key-insight] 选型最易搞错的点：FAISS 不是数据库
> FAISS 只是**算法库**——**无持久化、无 CRUD（删除常为惰性标记）、无元数据过滤、无分布式**。很多团队用 FAISS 做原型，上线才发现这些能力全缺、被迫重写。**测试视角**：用 FAISS 就要额外验证「索引持久化」「重启恢复」「并发读写」——**这是最容易漏测的部分**。

![向量索引与命名空间数据模型（Pinecone 官方）](../../_attachments/images/AI相关学习资料/RAG的流程与应用/10-向量索引与命名空间数据模型-pinecone官方.png)

*图 10：Index → Namespace → Record 的数据模型。**命名空间是一个查询边界：跨命名空间记录彼此不可见**，因此可用来隔离租户或环境（也是测试必须验证的隔离边界）。*

| 数据库 | 类型 | 核心优势 | 主要限制 | 适用规模 |
|---|---|---|---|---|
| **Milvus** | 开源分布式 | 索引类型最丰富、分布式、GPU | ⚠️ 运维复杂（需 K8s） | 十亿–千亿 |
| **FAISS** | **算法库（非数据库）** | 内存内检索最快、Meta 验证 | ⚠️ 无持久化/CRUD/过滤/分布式 | 千万级以内、离线批处理 |
| **Pinecone** | 商业托管 | 免运维、Serverless、SLA | ⚠️ 供应商锁定、成本高 | 百万–百亿 |
| **PostgreSQL + pgvector** | 传统库扩展 | **过滤能力极强（复用 SQL）**、事务一致 | 超大规模扩展性有限 | 千万级以内 |
| **Redis（RediSearch）** | 传统库扩展 | 内存级速度、可复用现有 Redis | 成本随内存上升 | 中大规模 |
| **Chroma** | 开源轻量 | **零配置、Python 原生** | ⚠️ 不适合大规模生产 | 百万级以下、原型 |

**五条选型决策规则（可直接用于架构评审）**：① 数据能否出网（不能 → 排除托管云，只能自建）；② 有无 K8s 运维能力（无 → pgvector / Chroma / 单机 Milvus）；③ 过滤需求重不重（重 → pgvector 优势明显）；④ 规模（< 100 万 → Chroma/pgvector；100 万–5000 万 → HNSW 系；> 5000 万 → Milvus/DiskANN/分布式）；⑤ 团队熟悉度（已在用 PG → 优先 pgvector）。

**Chroma 的定位**：不是替代 Milvus，而是**替代「原型阶段不该引入的复杂度」**。边界必须明确——无分布式、过滤性能随数据量退化，**不适合作为企业级生产主库**；正确用法是「**Chroma 验证 → 契约测试 → 迁移到生产库**」。它在测试场景中有两个独特价值：**作为 RAG 测试的内存夹具**（`EphemeralClient` + function 级 fixture，用例间零污染、可进 CI 不依赖外部服务）、**作为契约测试的参考实现**。

**测试视角（存储层）**：核心是**契约测试**——同一套 `contract_test`（最近邻语义正确、元数据/命名空间隔离、upsert 幂等、删除彻底）跑遍所有候选实现，作为选型迁移的回归保障。其余：持久化与恢复、删除彻底性（**无幽灵索引**）、命名空间隔离（跨命名空间零可见）、并发一致性、冷启动性能。

> [!key-insight] 选型中最容易踩的坑
> **「带过滤条件的检索性能」比「无过滤的基准性能」更值得测**。过滤会改变候选集分布，某些实现在**高选择性过滤**（过滤后只剩极少数据）时性能急剧退化。做法：准备 1% / 10% / 50% 命中率的三组过滤条件分别测延迟。

## 五、内核层：IndexFlatL2 / IVF-PQ / HNSW（第 5 章）

> **本章定位**：讲「**凭什么在一亿条向量里秒级找到最近的几条**」。**所有 ANN 索引都是「用召回率换速度」的近似算法**——HNSW 召回率不是 100%，IVF-PQ 会引入量化误差。**不知道「近似」这件事，就会把「检索结果偶尔偏差」当 bug 报，或更糟——把「召回率不达标」当正常放过。**

| 算法 | 核心思想 | 时间复杂度 | 召回率 | 内存 | 建索引 |
|---|---|---|---|---|---|
| **IndexFlatL2（FLAT）** | 全量遍历，精确计算 | **O(N·D)** | **100%（精确）** | 低 | 最快 |
| **IVF-PQ** | K-Means 分桶 + 向量压缩 | **O(√N)** 量级 | 90–95% | **最低**（压缩约 60×） | 快（需先训练） |
| **HNSW** | 多层图 + 贪婪搜索 | **O(log N)** | **95–99%** | 高（图结构额外占用） | 慢 |

> **一张图记住三者关系**：**FLAT 是「把书从头翻到尾」，IVF-PQ 是「先按目录定位章节再粗读」，HNSW 是「先看目录的目录，逐层下降，最后在小范围精读」。**

### 5.1 IndexFlatL2 —— 测试工程师的「裁判」

暴力检索，**召回率恒为 100%**，无训练阶段。三个不可替代的用途：① **作为正确性基准（Ground Truth）**——评估 HNSW/IVF-PQ 的召回率必须拿它做对照，**没有 FLAT 就无法量化 ANN 的召回率**；② 小规模（10 万条以内）的最终方案，零近似误差；③ 作为回归测试的**参考检索器**，持续监控召回率是否劣化。
**工程细节**：Faiss 选 L2 度量时**只计算平方根之前的距离值**（开方是单调变换，不影响排序）——**断言时取到的是平方距离，不是真实欧氏距离**。

### 5.2 IVF-PQ —— 两级近似的叠加

- **IVF（倒排文件）**：用 K-Means 聚成 `nlist` 个簇，检索时只探最近的 `nprobe` 个簇。参数经验：`nlist ≈ √N`；`nprobe` 起始 1–16，调大召回升、延迟升。
- **PQ（乘积量化）**：把向量切成 M 个子向量，每段用码本编号表示。768 维 float32（3072 字节）→ 约 96 字节，**压缩约 32–60 倍**，代价是量化误差；距离在「码本编号」上查表计算。

> [!key-insight] IVF 召回率低于 HNSW 的根本原因（面试必答）
> **如果正确向量所在簇没被选中，就永远找不回来。** `nprobe` 就是「多探几个簇以提高容错」的旋钮。另外 **IVF 需要「训练」阶段，且数据分布变化后需重新训练**——这是它与 HNSW 的重要工程差异。
> 变体对照：IVF_FLAT（不压缩，精度高）/ IVF_SQ8（省约 75% 内存）/ IVF_PQ（内存最低）/ IVFADC-R（三级量化 + 残差重排，十亿级高精度）。

![PQ 乘积量化技术族谱（Faiss 官方）](../../_attachments/images/AI相关学习资料/RAG的流程与应用/11-PQ乘积量化技术族谱-faiss官方.png)

*图 11：PQ 技术族谱。**Faiss 中已实现的方法用红色高亮**——这是选型时判断「某库声称的 PQ 支持对应哪一代方法」的依据。*

### 5.3 HNSW —— 当前 RAG 最主流的 ANN 索引

核心思想来自两个直觉：**小世界网络**（每节点连几条远距离边，任意两点只需很少跳数）+ **跳表式分层**（多层图加速查找）。上层稀疏长连接负责**快速跨越**，下层密集短连接负责**精确落点**。

![HNSW 分层图结构（Weaviate 官方）](../../_attachments/images/AI相关学习资料/RAG的流程与应用/12-HNSW分层图-weaviate官方.png)

*图 12：多层图结构。层数越高节点数指数级减少；layer 0 包含全部节点与短距离局部连接；连接是双向的。*

![HNSW 搜索过程（Weaviate 官方）](../../_attachments/images/AI相关学习资料/RAG的流程与应用/13-HNSW搜索过程-weaviate官方.png)

*图 13：搜索过程——从最上层入口点开始贪婪搜索，逐层下降、范围逐层收窄，到 layer 0 后找到最近的 K 个节点。*

![HNSW 节点插入过程（Weaviate 官方）](../../_attachments/images/AI相关学习资料/RAG的流程与应用/14-HNSW节点插入-weaviate官方.png)

*图 14：插入过程与搜索高度相似——先「搜索」找到合适位置，再与最近邻居建立双向连接。这解释了 HNSW 建索引为何比 IVF 慢：每插入一个节点都要跑多次贪婪搜索。*

**四个关键参数（必背）**：

| 参数 | 阶段 | 含义 | 调大 | 常用值 |
|---|---|---|---|---|
| **M（maxConnections）** | 建索引 | 每节点最多连接多少邻居 | 召回率↑、内存↑ | 16–32（底层通常 2×M） |
| **efConstruction** | 建索引 | 建索引时保留的候选集大小 | 索引质量↑、建索引更慢 | 100–200 |
| **efSearch（ef）** | **查询** | 查询时保留的候选集大小 | 召回率↑、查询更慢 | 50–200 |
| **distance** | 配置 | 距离度量（cosine / dot / L2） | — | 与归一化状态匹配 |

![HNSW 关键参数（Weaviate 官方）](../../_attachments/images/AI相关学习资料/RAG的流程与应用/15-HNSW关键参数-weaviate官方.png)

*图 15：四个关键参数——ef（查询候选集）、efConstruction（**只在建索引阶段生效**）、distance（度量）、maxConnections（底层更高）。*

> [!key-insight] 参数调优口诀（高频追问）
> **「M 和 efConstruction 决定索引有多好，efSearch 决定你用多大力气去找。」** 前者是一次性投入，后者**每次查询都可调**——所以**召回率不够时，先调 efSearch**（可在线调整，无需重建索引）。

**HNSW 的四个已知局限**：① 内存占用高（图结构额外占用，可结合 PQ 量化）；② 建索引慢；③ **删除是惰性的**（标记删除 + 查询时过滤，节点仍占图空间，需重建才真正释放）；④ 层数**按指数分布随机分配** → **建索引结果不可复现**。

> [!gap] 三个最容易被测试遗漏的 HNSW 坑
> 1. **惰性删除**：删除后仍占位 →「删了 10 万条内存几乎没降」是**已知行为不是 bug**。断言要写两条：**功能上不可被召回 + 资源上不会立即释放**。
> 2. **结果不可复现**：层数随机分配导致建索引不确定 → **断言必须用「召回率区间」而非「结果精确匹配」**，否则会产出大量假失败。
> 3. **召回率巡检常态化**：用 FLAT 做基准，**每周跑一次 Recall@K**——这是唯一能发现「索引质量静默劣化」（数据漂移、参数被误改）的手段。

**测试视角（内核层）**：FLAT 扮演**「裁判」**角色（价值不在上线，而在提供可信对照基准）。IVF-PQ 要**分层定位**——簇覆盖率（扫描 nprobe 找达标最小值）、**簇边界风险**（查询向量位于两簇中间的用例）、量化误差（**不应导致排序翻转**）、训练集代表性（分布漂移会静默降低召回，需触发重训）、未训练即检索必须明确报错（**不得静默返回随机结果**）、内存声明一致性。

## 六、实战层：HR 问答与医疗混合检索（第 6 章）

**实战一 · HR 制度智能问答**——选 RAG 而非微调，因为：制度频繁更新（改索引即可）、必须可溯源、权限分层、问法口语化、答案必须准确。**系统五层**：① 数据层（结构感知切分，制度天然有「章-条」结构）→ ② 元数据层（`dept`/`version`/`effective_date`/`level`，权限与版本过滤依据）→ ③ 向量层（**本地 Embedding**，同时保留 BM25 稀疏索引）→ ④ 检索层（意图识别 → 混合检索 → Rerank，**预过滤必须在相似度计算之前**）→ ⑤ 生成层（Prompt 强制引用条款号，无法回答时明示「制度中未找到」）。
**三个被真实痛点逼出的设计决策**：**必须混合检索**（「五险一金」是语义问题，「第 3.2 条」是精确问题）、**必须做意图识别**、**必须强制引用**。

**实战二 · 医疗实体命名混合检索**——三个关键差异：术语体系复杂（心梗 / 急性心肌梗死 / AMI 是同一实体，**必须语义检索**）、精确标识符必须精确匹配（药品名 / ICD 编码，**必须关键词检索**）、合规要求最严（PHI 不得出网）。**两个「必须」并存 → 结论是医疗场景必须用混合检索。**

| 融合策略 | 做法 | 优势 | 局限 |
|---|---|---|---|
| 加权求和 | `α·向量分 + (1-α)·关键词分` | 简单可解释 | α 需调参，量纲不同需归一化 |
| **RRF（Reciprocal Rank Fusion）** | `Σ 1/(k + rank_i)`，按排名融合 | ✅ **无需归一化、鲁棒、工业界常用** | 丢弃分数绝对大小信息 |
| 级联 | 一路粗筛，另一路精排 | 性能好 | 前置路的召回上限决定整体效果 |

> [!key-insight] 面试加分点
> **RRF 比加权求和更常用**——它**只用排名、不用分数**，回避了「向量相似度（0–1）」与「BM25 分数（无上界）」量纲不可比的问题；被追问「两种检索分数怎么融合」时答「优先 RRF」即加分。医疗场景还需**实体感知检索**：查询「心梗」→ 实体归一化 → 展开全部别名 → 多路检索 → 合并精排。**脱敏红线**：只替换身份证远远不够——病历中存在大量**间接标识**（「患者丈夫电话 138…」），必须**正则规则库 + NER 双重过滤**，并用**反向扫描**验证零残留。

**RAG 验收的五个层次（顺序不可颠倒）**：

| 层 | 验收目标 | 关键指标 | 通过标准 |
|---|---|---|---|
| ① 数据正确性 | 入库一致、脱敏彻底、无重复 | 一致率 / 残留数 / 重复率 | 残留 = 0；一致率 ≥ 99% |
| ② 检索质量 | 该找到的能找到、排序合理 | Recall@K / Precision@K / MRR | Recall@5 ≥ 0.85；MRR ≥ 0.8 |
| ③ 生成质量 | 忠实于上下文、切题、引用准确 | Faithfulness / 引用准确率 | Faithfulness ≥ 0.85；引用 ≥ 0.9 |
| ④ 安全合规 | 权限不越界、数据不出网、可审计 | 越权数 / 外网调用数 | 越权 = 0；外网 = 0 |
| ⑤ 性能 | 满足 SLA | P95 检索与端到端延迟 | 按业务 SLA（常 3–5s） |

> [!key-insight] 为什么顺序不可颠倒
> **脏数据上跑出的任何指标都不可信**——数据层没过，②③④⑤ 全都不用跑。而**调优排查顺序与验收相反（从下游往上游查）**：答案错 → 先看检索结果里有没有期望文档（没有 → 检索问题；有 → 生成问题）→ 再看引用是否正确 → 最后看权限是否生效（越权 → 检查是否误用 Post-filter）。

**测试视角（实战层）**：把「五层验收」固化成可重复执行的质量门禁——作为**上线门禁**（任一层不通过则阻断发布）、**日常巡检**（每周看 Recall@5 与 Faithfulness 趋势）、**变更回归**（切分参数 / Embedding 模型 / 索引参数 / Prompt 任一变更都要跑完整验收）、**评测集维护**（版本化 + bad case 回流）。**混合检索必须证明「优于单路」**，否则它就是纯粹的技术债；**「数据不出网」是可测的**——用网络 spy 挂到查询链路做断言。

## 七、面试考点速览（第 7 章）

**高频考点（按层速查）**：

| 层 | 核心考点 | 一句话答案 |
|---|---|---|
| 价值 | RAG 与微调怎么选 | RAG 改**输入上下文**（知道什么），微调改**模型权重**（怎么表达）；事实+风格并存则两者叠加 |
| 数据 | 预过滤 vs 后过滤 | **企业只能用 Pre-filter**——语义相似度不是访问控制机制 |
| 向量 | 换 Embedding 模型的风险 | **必须重建全部索引**，否则检索整体劣化且**不报错**（静默失真） |
| 向量 | Top-K 怎么设 | Recall@K 曲线找饱和点；K 过大会触发 **Lost in the Middle** |
| 存储 | 向量数据库 vs FAISS | FAISS 只是**算法库**，无持久化/CRUD/过滤/分布式 |
| 内核 | IndexFlatL2 的价值 | 100% 召回，**是所有 ANN 的「正确性基准」**；复杂度 O(N·D) |
| 内核 | IVF 的原理与风险 | 只探 nprobe 个簇；**正确向量所在簇未被选中就永远找不回** |
| 内核 | PQ 的价值 | 768 维 float32 → 约 96 字节，**压缩约 32–60 倍**，代价是量化误差 |
| 内核 | HNSW 核心思想 | 多层图 + 贪婪搜索，O(log N)，召回率 95–99% |
| 内核 | HNSW 四个参数 | M / efConstruction 定质量（一次性），**efSearch 可在线调，召回不足先调它** |
| 内核 | HNSW 的三个坑 | 内存高 / 建索引慢 / **惰性删除** / **结果不可复现** |
| 实战 | 为什么需要混合检索 | 向量管语义（五险一金↔社会保险），关键词管精确标识符（条款号、ICD） |
| 测试 | 答案错了怎么定位 | 二分法：Top-K 里有没有期望文档 → 检索问题 or 生成问题 |
| 测试 | 如何持续监控检索质量 | 用 **FLAT 做基准**定期跑 Recall@K——发现索引静默劣化的唯一可靠手段 |

**通用四步答题框架**：**① 明确被测对象与边界**（RAG 是「离线索引 + 在线检索 + 生成」三条链路的组合，离线产物质量是所有在线测试的前提）→ **② 分层给测试维度**（数据 → 检索 → 生成 → 安全 → 性能五层，每层 2–3 个维度）→ **③ 给关键用例与断言方式**（每层至少一个具体用例，说明断言什么、阈值多少——**这一步是区分「背概念」与「真做过」的分水岭**）→ **④ 给质量闭环**（评测集版本化、上线门禁、定期召回率巡检、bad case 回流）。

**追问速查**：「检索分数高为什么答案还错？」→ 从联合概率公式切入（检索分布与生成条件分布是两件事）→ 引出 Rerank；「HNSW 召回率为什么不是 100%？」→ 它是**近似**算法，用召回率换速度，用 FLAT 做基准可量化差距；「怎么防止幻觉？」→ 三层：上下文约束 + 拒答机制 + 量化监控（Faithfulness）。
