## 第一章 模型背景与核心介绍

### 1.1 一句话说清 Jev 是什么

> **Jev 是一个"聪明的 if 语句"**：你给它一段非结构化的程序状态（state），再给它一组**预先定义好答案形状**的类型化问题（questions），它**不生成任何文字**，直接返回**带概率的类型化判断**，供你的代码分支。

把这句话拆开，三个关键点缺一不可：

| 关键点 | 含义 | 与 LLM 的差别 |
|--------|------|--------------|
| **只有类型，没有文本** | 输出被约束为 Choice（选一个）/ Score（打一档）/ Noul（是不是） | LLM 生成字符串，需要解析、校验、重试 |
| **答案空间由你定义** | 所有可能答案在你调用前就写死了 | LLM 自由生成，可能编出你没给的选项 |
| **每个答案都带概率** | 概率经过"校准"训练，可当阈值用 | LLM 即使被要求给置信度，也普遍过度自信且不一致 |

官网与其他 AI 工具的角色对比：

```
工具                你给它的              它还给你的              它的角色
────────────────────────────────────────────────────────────────────────
ChatGPT            提示词/对话           生成的回复              通用助手
Cursor             编程任务+仓库+工具    代码改动/命令/测试结果   编辑器 & 编程 Agent
Codex / Claude Code 一条指令+本地工具     工具调用/改动/终端结果   终端编程 Agent
Jev                状态 + 类型化问题     选择 / 分值 / 概率       ★软件内部的"判断原语"
```

**最重要的一句定位**：Jev 不是来取代这些工具的，而是**嵌进它们内部**。比如编程 Agent 在执行一条 shell 命令前，可以问 Jev "这条命令是只读、可逆、还是破坏性的"，再决定是否放行。

### 1.2 公司背景与创始人

创始人 **Diogo Almeida** 的公开自述（官方博客原文）：

> "At OpenAI, I helped build the methods that made language models useful at following instructions and talking with people. That work ended up as the research behind ChatGPT. ... I thought maybe chat models would lead to AGI, but despite the hype it became obvious to me that there was something really big missing."

他的核心质疑是：**"模型在对话上早就超越人类了，那自动化在哪里？"（Models have been superhuman at chat for years, so where is all the automation?）**

他的诊断是：过去所有优化都指向"人类偏好"——产出人类评分高的文字。但**计算机不需要文字，计算机需要结构化的数据**才能在软件流水线里可靠运行。于是团队在隐身状态（stealth）研发两年，做出了第一条产品线。

### 1.3 命名来源：两个"彩蛋"

理解名字，等于理解这家公司的世界观。

**（1）System One 模型**：取自 Daniel Kahneman 的《思考，快与慢》——
- **系统 1（System 1）**：快速、直觉、不费力的判断
- **系统 2（System 2）**：缓慢、深思熟虑的推理

TypeSafe 的主张是：**软件内部绝大多数决策本质上是"系统 1 判断"**（"这属于哪个桶？""这紧急吗？"），但产业界一直在**租用"系统 2"模型来做"系统 1"的事**。Kahneman 认为系统 1 "易出错"，而 TypeSafe 声称 System One 模型可以通过专门训练变得**比替代方案更可靠**。

**（2）Jev**：取自经济学家 **William Stanley Jevons** 与 **杰文斯悖论（Jevons Paradox）**——1865 年 Jevons 观察到，蒸汽机效率提升并没有减少煤炭消耗，反而让煤被用到了更多地方、总需求暴涨。

TypeSafe 的赌注：**智能的单位成本每下降一个数量级，就会解锁数量级更多的用例。**

### 1.4 三种原语：Jev 的全部 API

整个 API 只有三种问题类型。**这不是限制，这就是设计。**

```
┌─────────────────────────────┬─────────────────────────────┬─────────────────────────────┐
│          CHOICE             │           SCORE             │            NOUL             │
│         分类选择             │          量表评分            │          真伪判断            │
├─────────────────────────────┼─────────────────────────────┼─────────────────────────────┤
│ 从选项表中选一个              │ 在有序档位上定位             │ 某陈述成立的概率             │
│ • 最多 255 个选项            │ • 2–10 个有序档位            │ • 二值假设检验               │
│ • 每个选项可带语义描述        │ • 档位用自然语言描述         │ • 输出 [0, 1] 连续概率       │
│ • 返回 choice/probabilities  │ • 返回 score/probabilities   │ • 返回 noul                  │
│   /confidence               │   /confidence               │ • ★无 confidence 字段        │
│ 替代：枚举 / 路由器           │ 替代：情感/紧急度打分         │ 替代：布尔值                 │
└─────────────────────────────┴─────────────────────────────┴─────────────────────────────┘
```

**请求 / 响应示例**（官方文档结构，数值为示意）：

```json
// 请求
{
  "model": "jev-latest",
  "state": { "opportunity": "link", "name": "Managed Postgres",
             "description": "We make a managed PostgreSQL hosting product..." },
  "questions": {
    "is_sponsor_inquiry": { "type": "noul",
      "instructions": "Does `description` ask to sponsor the site or newsletter?" },
    "product_category": { "type": "choice",
      "instructions": "What kind of product is described by `name` and `description`?",
      "criteria": { "dev_tool": "Developer tools, hosting, APIs, SaaS for developers",
                    "course": "Courses, books, or training",
                    "unrelated": "Anything not aimed at developers" } },
    "message_quality": { "type": "score",
      "instructions": "How specific is the request?",
      "criteria": ["Generic template, no reference to this site",
                   "Mentions the site but no concrete ask",
                   "Concrete ask with a timeframe or product named"] }
  }
}
```

```json
// 响应
{
  "model": "jev-1.13.0",
  "answers": {
    "is_sponsor_inquiry": { "type": "noul", "noul": 0.99 },
    "product_category": {
      "type": "choice", "choice": "dev_tool",
      "probabilities": { "dev_tool": 0.97, "course": 0.01, "unrelated": 0.02 },
      "confidence": 0.95 },
    "message_quality": {
      "type": "score", "score": 1.9,
      "legend": { "0": "Generic template...", "1": "Mentions the site...", "2": "Concrete ask..." },
      "probabilities": { "0": 0.0, "1": 0.1, "2": 0.9 },
      "confidence": 0.86 }
  },
  "usage": { "input_tokens": 210, "output_tokens": 31 }
}
```

**三个必须注意的机制**：

1. **一次调用、并行求解**：请求里的每个问题**独立地**对照同一份 state 评估，一次算完。加第四个问题几乎不改变响应时间——官方明确说"增加问题不会造成上下文腐烂（context-rot）"。
2. **答案不可能越界**：`product_category` 只能是 `dev_tool`/`course`/`unrelated` 三者之一，模型**发明不出第四类**。这就是"零幻觉"声称的真实含义——**结构保证，不是语义保证**。
3. **原子化问题，在代码里组合**：官方强烈建议把复合判断拆成多个独立问题（比如不要问"给这份创业计划书打分"，而要分别问市场规模、技术可行性、差异化），然后**用自己的代码加权组合**。这样权重变化时改的是代码里的系数，而不是重写 prompt。

**关于置信度的关键澄清**（官方 confidence 文档）：

- `confidence` 是**从概率分布的"形状"推导出的统计量**：全部集中在一个选项上 = 1.0；分布越平均，置信度越低。
- 官方给出的三选项近似公式：`(3 × 最大概率 − 1) / 2`。
- **Noul 没有 confidence 字段**，因为那个概率本身就是信念值。
- 官方明确说：**校准是在"成组预测"上度量的，不保证单次答案正确。**
- **推荐的三段式路由**：
  ```
  高置信度 → 自动执行
  中置信度 → 谨慎推进（要求用户确认 / 标记待复核 / 补充信息）
  低置信度 → 不执行，转人工 / 请求澄清 / 降级到其他系统
  阈值随风险变化：破坏性操作的自动执行阈值，必须高于只读操作。
  ```

### 1.5 技术架构：并行采样器 + RLCD

官方博客把技术栈概括为三根支柱：

```
① 新模型架构（未公开细节）
② 并行采样器（parallel sampler）—— 一次查询产出全部输出
③ RLCD 训练法（Reinforcement Learning for Calibrated Decisions，校准决策强化学习）
```

**（1）架构核心：不做自回归**

| 维度 | 传统 LLM | Jev |
|------|---------|-----|
| 采样方式 | **串行**：一次一个 token，每个 token 以前面所有 token 为条件 | **并行**：一次查询产出全部输出，硬件感知 |
| 延迟来源 | 生成长度决定耗时（复杂结构化抽取要数秒） | 与问题数几乎无关（70–500 ms） |
| 输出单位 | 字符串 | **类型本身**（不是"生成文本再解析成类型"） |

一个通俗类比（来自第三方解读）：LLM 像**手写报告**，一页页写；Jev 像**驾驶舱仪表盘**，直接亮灯。

> ⚠️ 注意：architectural 细节**未公开**。官方既未发布架构论文，也未公布参数量、权重或自托管方案。第三方观察到 Jev 的 Noul 与等价的 yes/no Choice 会给出**不一致**的答案，这反证其内部确实对不同原语使用了不同机制——但机制是什么，官方没说。

**（2）RLCD：与 RLHF 的分野**

这是理解 Jev 的**最关键一处**，也是面试高频点。

```
RLHF（现有主流）
  监督微调 → 人类标注者两两比较模型回复、选出更喜欢的 → 训练奖励模型 → 用奖励模型优化 LM
  优化目标：人类偏好
  副作用：① 过度自信（模型会"听起来很笃定"，哪怕毫无依据）
         ② 模式坍缩 / 模式丢弃（mode dropping，忽略有效但不够讨喜的答案）
  适用前提：★有人来读输出

RLCD（Jev）
  保留 RL 回路，但把"人类偏好"替换为另一个目标：
  → 模型自报的置信度，应该匹配它实际正确的频率
  → 大量预测中，报 70% 的那些，应有约 70% 正确
  优化目标：与结果一致的、认识论上诚实的概率
  实现：在可程序化验证奖励的任务上训练；用 Brier 分数、负对数似然等严格评分规则
  适用前提：★由软件来消费输出
```

**为什么这件事重要**：一个 API 说"0.9"却只有 60% 的时候是对的，**不管它的文笔多好，都不能进入自动化流水线**。Jev 的全部商业逻辑就建立在这个判断上。

> 🔴 **一处学术澄清**：RLCD 这个缩写存在同名冲突。2023 年 Yang 等人的论文中 RLCD 指 **Reinforcement Learning from Contrastive Distillation（对比蒸馏强化学习）**，目标是用对比提示构造偏好对、模拟 RLHF 数据。TypeSafe 的 RLCD 指 **Reinforcement Learning for Calibrated Decisions**，是完全不同的目标。**不要把 2023 年那篇论文当作 Jev 的技术文档。**

### 1.6 接口、SDK 与价格

**Python（官方示例）**：

```python
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

client = TypeSafeClient()          # 从环境变量 TYPESAFE_API_KEY 读取密钥

resp = client.system_one(
    state={"ticket": {"subject": "Duplicate charge",
                      "messages": [{"from": "customer",
                                    "text": "I was charged twice for order A-104."}]},
           "order": {"id": "A-104",
                     "charges": [{"amount_usd": 49, "status": "captured"},
                                 {"amount_usd": 49, "status": "captured"}]}},
    questions={
        "department": Choice(
            instructions="Which team should handle this",
            criteria={"billing": "Payment issues",
                      "technical": "Bugs",
                      "sales": "Pricing or account questions"},
        ),
        "is_urgent": Noul(instructions="The message conveys urgency"),
        "frustration": Score(
            instructions="How frustrated the customer appears",
            criteria=["Calm, just stating facts",
                      "Frustrated but civil",
                      "Very angry, strong language"],
        ),
    },
)
print(resp.answers["department"].choice,
      resp.answers["department"].confidence,
      resp.answers["is_urgent"].noul,
      resp.answers["frustration"].score)
```

| 输入 | $0.042 / 百万 token | $0.20 – $10 / 百万 token |
| 输出 | **免费**（"便宜到不值得计量"，因为没有输出 token） | 约为输入的 5 倍 |
| 每 100 万次分类（每次 500 token）估算 | ≈ $21 | Claude Haiku 4.5 ≈ $550；Sonnet 5 ≈ $1,100 |
| 打分 100 万条 1,000 token 记录（24 类） | ≈ $42（含输出） | 量级高 1–2 个数量级 |

> **"输出免费"不是促销手段**，而是架构的直接结果：没有自回归生成，就没有可计量的输出 token。

## 第二章 迅速走红的原因

### 2.1 时机：Agent 撞上了"效率墙"

**这是最本质的原因。** 用中信证券研报的表述来概括：

> 现阶段 Agent 运行效率、效果仍有待提升。目前 Agent 单任务中各个步骤**全部交给 LLM 判断**，模型不仅要理解问题，还要花时间生成一段**最终不会被人阅读、只供程序提取结果**的文本，而 Jev 可以直接给出判断，省去逐 token 生成文本的中间过程。

换句话说，行业痛点是具体的、可量化的：

```
一个 Agent 任务里的决策构成
├── 少量"真难题"     → 复杂规划、疑难分析、高难度代码   → 需要前沿模型（系统 2）
└── 大量"小判断"     → 路由、分类、验证、护栏、参数填充   ← 一直在用昂贵的系统 2 来做
                       每个判断都付出：秒级延迟 + token 生成成本 + 解析/校验代码
```

Jev 填的是**这个还没被 LLM 很好解决的生态位**。它不宣称 AGI 贡献，而是"填补一个空缺"。

### 2.2 指标冲击力

首页那句 **"快 193.6 倍、便宜 444.6 倍"** 传播力极强。官方披露的单次对照：

| | Jev | GPT-5.6 Terra |
|---|---|---|
| 耗时 | **0.114 s** | 8.566 s |
| 成本 | **$0.000081** | $0.013880 |

不过官方博客自己也写了 **"我们预计这些是现实收益的上限"**，而这句话在转载中基本被丢掉了。第三方转述的区间通常写成"快 20–200 倍、便宜 40–400 倍"。

### 2.3 创始人光环

"ChatGPT 共同发明者做了个只做选择题的模型"——这个叙事本身就有巨大的传播势能。Diogo Almeida 是 RLHF / InstructGPT 那条线出来的前 OpenAI 研究员，**他"背叛"了自己参与创造的技术路线**，转向"不生成文字"的模型，这个反差极大。

### 2.4 生态在五天内爆发

按 2026-09-20 的 GitHub 搜索接口统计（名称或描述同时含 jev + typesafe 的新建仓库）：

```
1204 个仓库
├── 48 个   "awesome-jev" 类清单（同一件事被列了 48 遍）
├── 64 个   标注 MCP 的封装
└── 61 个   标注 skill、给各家编程 Agent 用的
```

**更强的信号是"平替的出现速度"**：
- **SemIf（原名 OpenJev）**：9 月 16 日建仓——**离官方博客发出不到一天**。README 开头就是 "Wow! No waitlist."。做法是用一个**冻结的 Qwen3.5-4B**，把 state 和问题拼成提示、只跑一次前向、直接读选项 token 的 logits 做 softmax，**一个 token 都不生成**。
- 后续跟进了 jeff（GLiFormer 400M）、von（395M）、openJev-verdict-2.0（ModernBERT 150M）等自托管替代。

**Vercel 侧的采用数据同样惊人**：发布后 24 小时内，Jev 在 Vercel AI Gateway 上被**近 13% 的付费团队**使用，是该平台史上采用最快的一次模型发布。需求集中涌入一度**打爆了 TypeSafe 的 API**。

### 2.5 叙事：Jevons 悖论

"每次智能成本下降一个数量级，就会解锁数量级更多的用例"——这个叙事把 Jev 从"又一个分类器"提升到了"重新定义 AI 调用发生的位置"。

官方描绘的图景是：**判断模型可能"消失"在代码里**——藏在客服队列、事件管道、垃圾过滤、权限检查内部，一次用户操作可能触发若干个小判断，却完全不露出 AI 界面。一个人一天可能只打开几次 ChatGPT，而普通软件可能在后台做成千上万次微型判断。

## 第三章 与传统大模型的关键区别

### 3.1 三方对比总表

> 注意：**把 Jev 只和 GPT 类模型对比是"容易的比较"**（它本来就不是 LLM，当然更快）。真正有价值的对比是**三方**——还要拉进"训练好的分类器"。

| 维度 | **Jev（决策模型）** | **前沿 LLM** | **微调编码器（BERT 系）** |
|------|-------------------|-------------|------------------------|
| 优化方法 | RLCD（校准决策强化学习） | RLHF / RLVR | 监督学习 + 交叉熵 |
| 优化目标 | 认识论上诚实的概率 | 人类偏好 / 可验证奖励 | 标签拟合 |
| 输入侧重 | **结构化程序状态** | 顺序消息、对话 | 单条文本 |
| 输出 | **类型安全的结构化值** | 字符串（聊天/代码/幻觉/拒答） | 固定标签 + 概率 |
| 采样 | **并行**（单次查询产出全部） | **串行**（逐 token） | 单次前向 |
| 延迟 | 70–500 ms | 3–329 s（同类问题） | 1–10 ms（自托管，无网络跳） |
| 价格 | $0.042 / MTok 输入，输出免费 | $0.20–$10 / MTok 输入 | ≈ $0（自有硬件） |
| 结构化输出错误 | **0%（构造性保证）** | LLM 侧 0.58%–45.5%（OpenRouter 数据） | 0% |
| 置信度 | 每个输出都带，经校准训练 | 常过度自信、不一致 | Softmax 分数偏过度自信，需温度缩放 |
| 是否需要标注数据 | **零样本**（运行时定义问题） | 零样本 | **必须**有标注 + 训练流程 |
| 改变问题 | 改一行 rubric 字符串，即刻生效 | 改 prompt | **重新训练** |
| 世界知识 | 预训练带来的零样本理解力 | 强 | 只有标注教会它的 |
| 数据私密性 | 只能通过 state/instructions 定制，**不能在你的数据上微调** | 同上（或私有部署） | **可完全用自己的数据微调、可离线运行** |
| 权重与厂商 | **闭源、仅托管 API** | 闭源/开源自选 | 开放、自持 |

### 3.2 架构差异：自回归 vs 并行采样

这是**性能差异的根因**：

```
LLM：输出 {"category":"billing","urgent":true}
     ├─ 生成 "{"        ← 依赖（无）
     ├─ 生成 "\"cat"    ← 依赖 "{" 
     ├─ 生成 "egory"    ← 依赖前面全部
     └─ ... 必须顺序生成每一个 token（O(n) 次前向）
     ⇒ 每个 token 都收费，且失败可能发生在产出合法对象之前
     ⇒ Schema 只能"约束 + 校验"，不能"保证"

Jev：所有问题对同一 state 并行求值
     ├─ question_1 ─┐
     ├─ question_2 ─┼─ 一次前向，互不干扰
     └─ question_3 ─┘
     ⇒ 输出的是"类型本身"，不是"文本被解析成类型"
     ⇒ schema 解析错误这一类生产故障被整类消除
```

### 3.3 训练差异：RLHF vs RLCD

已在 [1.5](#15-技术架构并行采样器--rlcd) 详述，此处补一张官方对照表：

| | 现有 LLM | System One + Jev |
|---|---|---|
| 优化于 | 人类偏好（人类评阅者喜欢的写作与聊天回复）；可验证奖励（可程序化验证的输出） | 校准决策（在 System One 任务上带"认识论诚实概率"的答案） |
| 输入 | 非结构化数据，侧重**顺序消息** | 非结构化数据，侧重**结构化程序状态** |
| 输出 | **字符串 / 生成文本**（灵活但需解析+校验，且总有"跑飞"风险） | **类型安全的结构化值**（输出与结构预先定义，永不产生类型错误） |
| 采样 | **串行** | **并行** |
| 置信度 | 即使被要求给置信度，也倾向过度自信、不一致 | 每个输出都传达置信度与不确定性；**更高置信度意味着更高准确率**；对相似输入返回相似答案 |
| 用例 | 人在环任务（聊天机器人、Copilot、编程 Agent）；可验证问题（数学证明、内核优化）；**演示原型** | **AI 驱动的工作流 / 智能 if 语句**；大数据 map-reduce；实时应用；**对一切做验证**（对 LLM 的 prompt、推理轨迹、输出做打分、裁判、护栏、越狱检测） |

### 3.4 应用场景差异

```
                     Jev 官方"不适合"清单                Jev 官方"适合"清单
                     ────────────────────────            ────────────────────────
需要产出文本          ✗ 写回复、写摘要、写代码             分类 / 路由 / 评分 / 抽取
需要开放式推理        ✗ 多步规划、疑难分析                 工作流分支（手写规则太脆的地方）
需要解释            ✗ 不提供理由、不可审计               大数据 map-reduce（把 PB 级数据变特征）
未知答案空间          ✗ 你必须能提前写出选项               实时应用（100ms 级，UX 敏感）
数学 / 日期比较       ✗ 见 jaggedness                     ★对一切做验证（LLM 输出的打分/裁判/护栏）
图像 / 音视频         ✗ 仅文本
```

**"验证"是官方最看重的场景**：$0.042/百万 token 这个价位，意味着开发者可以**筛查大模型的每一个输出**再让它触达用户或触发动作——这种监督在以前"太慢太贵，不可能对全部内容运行"。

### 3.5 关键澄清：Jev 不是"换个名字的 BERT"

这是最值得写进笔记的一节，因为它是**技术分歧的核心**。

官方与支持方的论点是"架构性的"：JSON 模式 / function calling 只是**约束了一个生成式模型的格式**，模型仍然以生成式方式推理、以生成式方式计费，其"置信度"（如果给的话）反映的是 **token 似然**而非**结果校准**。

怀疑方的论点（Hacker News 上的代表意见）是：**Jev 就是一个蒸馏过 / RL 调过的分类器，只是套了个"模型类别"的标签**；而且任何这类系统都会在**分布外输入**上悄悄失败。

**诚实的答案是两者都成立**：校准训练是真实的方法论差异，**分布边界也是真实的运营风险**——而置信度分数只有在"模型知道自己何时脱离分布"时才有帮助，这恰恰是校准**应该**度量、也正是批评者**怀疑**它没做到的地方。

第三方实测给出的分界线（详见 [4.3](#43-第三方实测与争议)）：

| 你的处境 | 更好的选择 |
|----------|-----------|
| 问题稳定、边界窄、量很大，**已有标注数据** | **微调编码器**（BERT 系）——更快、更便宜、可能更准，且数据不出内网 |
| **冷启动、还没有标注数据**、还不知道该分几类 / 阈值在哪 | **Jev**——零样本 rubric，改需求像提一个 PR，而不是跑一次训练 |
| 规则会**动态变化**，来不及重新训练 | **Jev**——它能"理解指令"，而静态分类器只会做字符串匹配 |
| 需要对**同一条输入并行问很多问题** | **Jev**——加问题几乎不加延迟；分类器则要 N 个模型或 N 个任务头 |

> **给 SDET 的一句话**：这本质上是"**你处在哪个阶段**"的问题，不是"哪个模型更好"的问题。

## 第四章 优势与局限性

### 4.1 优势清单

| # | 优势 | 说明与证据 |
|---|------|-----------|
| 1 | **结构性无幻觉** | 输出类型预先定义，模型**在数学上不可能**产出 schema 外的字段、破坏格式、或给出选项表外的答案。这是可被单个反例证伪的强声明，官方称"数学上不可能"。 |
| 2 | **消除一整类生产故障** | 不必再写 Pydantic / Zod / 正则去清洗 markdown 反引号、修补截断括号、对非法枚举值重试。**schema 解析错误在 Jev 运行时里不存在**。 |
| 3 | **置信度可用于工程** | 置信度从概率分布形状导出，并**按"高置信自动 / 中置信复核 / 低置信转人工"三段式**直接映射成代码分支。阈值可随操作风险分级。 |
| 4 | **延迟量级下降** | 70–500 ms vs 前排模型的秒级；第三方实测 p50 299 ms vs 同一权重 hosted 的 bart-large-mnli 5,131 ms（17.2×）。 |
| 5 | **单位成本量级下降** | 100 万次分类 ≈ $21（对比 Haiku 4.5 的 ≈ $550）。这是"可以对全部流量做监督"的价位。 |
| 6 | **一次调用、多问题并行** | 同一条 state 上问 8 个问题与问 1 个问题耗时几乎相同，且**不产生 context-rot**。 |
| 7 | **零样本、改需求成本极低** | 加一个问题 = 加一行 rubric；改一个选项 = 改一处 criteria 映射。**不需要标注、不需要训练、不需要部署新产物**。 |
| 8 | **接口极简** | 一个端点、三种原语。官方自己开源了 `system-one-adapter-python`，可以把任意 LLM 包成同一接口用于 A/B 对照或降级兜底。 |
| 9 | **生态在极短时间内成型** | MCP server、CLI、库、各编程 Agent 插件、Playwright 桥接等几十个项目在数天内出现。 |

### 4.2 官方自曝的 9 条缺陷（jaggedness）

> **这是全文最值得精读的一节。** TypeSafe 专门发布了一页 `Jev 1.13 jaggedness`（最后审阅 2026-09-17），列出自家的失败模式与规避方式。**几乎没有任何一篇发布报道走过这一页。** 官方自评：

> "jev-1.13 快、校准好、擅长常识判断，但它不完美。它在 System One 任务上表现最好，**在需要额外层级间接性的任务上可能吃力**，**理解可能相当字面**，**在需要数值精度的任务上挣扎**。"

| # | 失败模式 | 具体表现 | 官方建议做法 |
|---|---------|---------|-------------|
| 1 | **字面理解** | 回答"你写的问题"，而不是"你想问的问题"。限定词、否定、隐含条件都按字面读。反讽、低调陈述、礼貌性反话都可能读反。（"Great, another outage" 不是赞美） | 在 instructions 里写明**确切条件**；把边界情况放进 criteria。**当你在解释"我真正想说的是……"时，那句话就是指令缺失的另一半。** 无法避免解释歧义时，拆成两个字面问题，在代码里组合。 |
| 2 | **数学与数字** | **不是计算器**。**计数不可靠**（单词字符数、词在段落中出现次数、长列表项数），错误随被计数对象规模增长。**数值表示弱**：问颜色用 hex 值会明显弱于用英文颜色名；问高级编程语言强于问汇编/二进制指令。**不要用 Score 输出在两个档位之间插值还原精确数字**。 | **算术全部放代码里。** 计数：在代码里遍历候选项，**每项问一个 Noul**，然后自己加总。转换在代码里做，把算好的数字或命名分桶传给它。 |
| 3 | **日期时间比较** | 把日期当**文本**而非有序量。判断两个日期先后、相隔多久、是否落在窗口内都不可靠。 | 把日期成分抽成 Choice 问题（月、日、年，并显式加一个"未提及"选项），在代码里组装并比较。 |
| 4 | **多跳 / 间接性** | 准确率随双层否定与多跳推理下降。 | 直接写指令，**点名 state 里相关的部分**，减少跳数。 |
| 5 | **塞满无关细节的大 state** | 官方原话：**"Jev suffers from context rot"**——state 里与问题无关的内容会变成干扰项，拉低准确率。 | **先在代码里检索/过滤**，只发问题真正需要的东西；或用一条 Noul 先筛相关性。 |
| 6 | **对抗性内容** | 官方原话：**"State is data, and jev-1.13 does not treat it as hostile by default."**——state 里**注入的指令可以改变答案**。 | 在 criteria 中写明确，部署前测试边界用例。⚠️ **这意味着：用 Jev 做的提示注入过滤器，本身可被注入。** |
| 7 | **指令与标准互相矛盾** | 一条"true 意为 no"的 Noul 表现会变差。 | 把 criteria 当作 instruction 的延伸，**对齐措辞**。 |
| 8 | **常识性结构不变量** | 你默认成立的一致性**不保证成立**：同一工单问"顾客要退款吗"，用 Noul 问得 0.22，用 yes/no 的 Choice 问却是 `no` 0.99（置信度 0.97）；另一张工单"要退款"0.72、"要的是退款以外的事"0.47，**两者相加 1.19**。**互补概率不保证和为 1.0**。 | **每个决策只问一种方式**，不要在类型之间搬阈值；在代码里强制恒等式。 |
| 9 | **生成** | 未针对生成文本训练，靠串联 Choice 伪造生成既慢又差。 | 需要文本时**用生成式模型**，再让 Jev 挑出正确抽取。 |

**官方额外约束（不在上表中）**：
- **语言**：英语是主要训练语言、准确率最好；**其他语言处理较差**。第三方实测交叉验证：**中文表现明显不稳**，英文短文本才稳定。官方文档亦标注 CJK 准确率低。→ **中文场景必须用自己的内容先测。**
- 第 6 条对**任何读取用户提交文本**的系统都是现实关切，而非理论问题。

### 4.3 第三方实测与争议

这是判断"能不能上生产"的关键材料。**按可信度从高到低排**：

**（1）校准之争——最尖锐的一项第三方检验**（Charly Poly，banking77 数据集，77 类意图路由，真实人工标签、3 个随机种子、阈值在验证集上拟合并在留出测试集报告、24/24 次运行 0 错误）：

| 模型 | macro-F1（±std） | ECE（越低越好） | 备注 |
|------|-----------------|----------------|------|
| **Jev** | **0.782 ±0.009** | **0.105** | 报 80–95% 置信时，**实际只有 64% 正确** |
| ModernBERT-large-zeroshot（396M） | 0.712 ±0.020 | **0.081** | 报 80–95% 时，**实际 80% 正确** |
| bart-large-mnli | 0.453 ±0.013 | — | |
| gliclass-modern-base | 0.381 ±0.011 | — | |

结论三句话：
- **准确率 Jev 赢**（高约 7 个点）；
- **但在"校准"这个它名字里的卖点上，输给了开源编码器**——396M 的模型在笔记本电脑上跑，成本为 0；
- **Jev 整体过度自信约 10 个点**（自报 0.894 vs 实际 0.794）。

**最严重的一条**：**Jev 对"正确标签"给出恰好 0 概率的情况占 6.6%**；而三个开源模型在各自 1,155 次决策中**一次都没发生**。

> **为什么"0 概率"是致命的**：一个被模型宣告为"不可能"的决策是**不可恢复的**——没有阈值、没有兜底、没有重排序能救回来。

但同一测试也给出了 Jev **真正的胜利**：在验证集上设定"90% 精度"的阈值后，**Jev 可自动处理 67.5% 的流量，ModernBERT 只有 35.7%——同样的精度门槛下，自动化率约 2 倍**。该测试者自己的结论：「买它的速度，但要**验它的置信度**」。同时他也是"hosted vs hosted"对照下 17.2× 提速的验证者：「那一部分宣传是真的」。

**（2）MindStudio 的分类器对照测试**：

| 检验项 | 结果 |
|--------|------|
| Banking77 校准 | Jev 平均置信度 88%，实际准确率约 80%（轻度过度自信）；**事后温度缩放可把校准误差降低约 2/3** |
| vs 微调编码器+逻辑回归头 | 在 4 个数据集中的 3 个上，**小编码器胜出，有时大幅胜出**（因为它有任务专属标注数据） |
| **Jev 何时反超** | ① 没有标注训练数据；② 类别/路由规则动态变化来不及重训；③ 需要对同一输入并行问很多问题 |
| 动态指令跟随 | 路由策略**中途变更**时（取消涉及 100+ 席位的请求应转客户经理），**Jev 立即适应**，静态分类器继续套旧匹配模式出错。3 ms vs BERT 的 26 ms |
| 问题扇出 | 1 个问题约 150 ms；**打包 30 个问题耗时仍基本相同** |
| **最实用的模式** | 直接问"这封邮件是钓鱼吗"准确率仅 **≈60%**；把同一问题**拆成 8 个具体指标**、把结果喂给轻量下游分类器后，准确率升到 **94%** |

**（3）问题设计决定成败**（aitraining2u 汇总的第三方结果）：

| 测试 | Jev | 对照 | 值得注意 |
|------|-----|------|---------|
| 钓鱼邮件（单问，2000 封合成） | 62.6% | Haiku 4.5 81.3% | **一个两行正则拿到 91.8%** |
| 钓鱼邮件（拆 5 问，1000 封留出） | **95.0%** | Haiku 4.5 93.2% | 同一模型，**拆问题后从 62.6% → 95.0%** |
| 垃圾邮件（18,514 封） | 98.33% | TF-IDF 基线 98.39% | **廉价经典基线打平了它** |
| 事件筛选（50 例） | 96% | Gemini 3.5 Flash-Lite 86% | 样本小，仅作方向性参考 |
| 工具调用风险（60 例） | 91.7% | — | 重复运行得 91.7% 与 93.3%，**存在方差** |

**两条穿透性结论**：
1. **问题设计决定结果**——62.6% → 95.0% 只靠把一个问题拆成五个。
2. **无聊的基线很危险**——正则和 TF-IDF 在各自的主场上打平甚至超过了前沿价位的方案。**任何跳过基线的比较都是营销。**

**（5）反面证据——长时程任务彻底失败**：

> 在 Browser Use 创始人的**长时程浏览器测试**中，**Jev 得分 1/20，而具备推理能力的 Luna 得 17/20**。
>
> 解读：Jev 的强项是**短、封闭、可枚举**的判断；一旦任务需要跨多步维持目标与推理，它立刻暴露上限。此外，**精美的 demo 跑在干净沙箱里**——混乱的 DOM、异步加载、弹窗就会击穿它。

**（6）从业者的一句冷评**：

另一位早期用户（CtrlAltDwayne）：「它很快，但**它做的事，一个称职的工程师手工或借助 Astra/Fable 也能做**，我找不到它的用例。」——**这句批评最值得记录，因为它是"边界"而非"缺陷"**：Jev 的价值取决于你的调用量级与延迟要求，而不是"能不能做"。

### 4.4 产品级硬约束

| 约束 | 内容 | 影响 |
|------|------|------|
| **仅文本** | 不支持图像、音频、视频 | ❌ 不能做视觉 UI 定位、截图断言、OCR |
| **不开源、仅托管** | 无权重、无参数量、无架构论文、无自托管 | ❌ 不满足"不出内网/数据驻留/气隙环境"要求的团队（**对你的公司合规约束是硬伤**） |
| **服务区域** | 官方称服务部署在美国西海岸 | ❌ 跨境数据传输与延迟均有问题 |
| **上下文口径冲突** | 官方 docs：每请求 64k；state + 最长 question 32k。OpenRouter 标注 32k | ⚠️ 设计前必须核实 |
| **Choice 上限 255** | 超过需两阶段（先独立 Score 再显式 Choice） | ⚠️ 大规模元素表需分层 |
| **不能在你的数据上微调** | 定制只能靠 state 与 instructions | ⚠️ 领域专有语义需靠 rubric 设计补 |
| **基准全部自建自跑** | 跳过公开排行榜；参照答案是 GPT-6 Astra 与 Fable 5.1 的平均值；工作流由自家能力团队编写；**官方自认无法证明价格未被补贴** | ⚠️ 上线前必须自建评测 |
| **不提供理由** | 无 rationale 通道。分数低时你只能读自己的 criteria 来 debug | ❌ 审计、客诉、需解释的场景必须叠生成模型 |
| **无法弃权** | 强制二选一时，没有 unknown/needs_review 选项，它会挑"最不坏"的那个，而不是说"不知道" | ⚠️ 必须自己设计逃生出口 |

## 第五章 测试开发视角：Jev 能带来什么价值

### 5.1 先确立判据：一个问题是否"Jev 型"

在谈具体场景之前，先给一条**可复用的判据**。官方给的规则是：

> 一个好问题，是**一个知识渊博的人在给定正确上下文后，几秒钟内就能做出的判断**。

转化成工程判据：

```
✅ 是 Jev 型，当且仅当：
   ① 答案空间能在调用前写出来（选项 / 档位 / 是-否）
   ② 判断不需要扩展推理、不需要计算、不需要比较日期
   ③ 输出由代码消费，而不是由人阅读
   ④ 需要的是"不确定性"而不仅是"答案"（要阈值门控）
   ⑤ 同一个判断会跑很多次（成本/延迟才成为杠杆）

❌ 不是 Jev 型，如果：
   ① 你要的是文本（用例标题、步骤、报告、修复代码）
   ② 需要多步推理或长时程目标维持
   ③ 涉及算术、计数、日期先后
   ④ 答案空间事先不可知
   ⑤ 需要可解释性 / 可审计性
```

**一句话版本**：**"你知道答案空间吗？知道 → Jev；不知道 → 生成式模型。"**

而官方与中信证券的共识架构是**分工**，不是替代：

```
┌──────────────────────────────────────────────────────────────────────┐
│                        混合（Hybrid）架构                              │
├──────────────────────────────────────────────────────────────────────┤
│  代码（Code）    │ 拥有控制流、策略、权限、事务、阈值、审计日志           │
│  Jev（系统 1）   │ 高频小判断：分类 / 路由 / 评分 / 抽取 / 护栏 / 验证   │
│  LLM（系统 2）   │ 难题：复杂规划、疑难分析、写报告、写代码、要解释时     │
└──────────────────────────────────────────────────────────────────────┘
```

> 中信证券的判断：未来 Agent 可能"**工作流复杂规划、疑难分析和高难度代码任务交给前沿模型，路由、分类、验证等高频判断交给 Jev 这类决策式模型**，比如'用户目标是否完成''结果是否符合要求'等，以兼顾效果、速度与成本。"

### 5.2 场景 A：UI 自动化测试（重点）

这是与 SDET 最直接相关、也最容易被误解的场景。**必须先澄清一个致命误解**：

> ❌ **Jev 不能做视觉 UI 自动化。** 它不支持图像输入——官方连 Doom 演示喂进去的都是**结构化的游戏状态描述**，不是画面。所以"截图 + 多模态模型找元素"的路线与 Jev 无关。

**那它在 UI 自动化里的正确位置是什么？——"动作空间决策层"。**

```
传统 AI 浏览器 Agent（如 Playwright MCP 风格）
  整页快照 → 塞进 LLM 上下文 → LLM 决定点哪 → 执行
  ⇒ 每步都要把整页 DOM/截图喂给主模型：token 巨大、决策慢、成本高

Jev 路线（jev-ultrafast 的"动态索引动作空间"）
  ① 抽取页面 → 生成"编号元素表"
        [1] button    Change ticket type · Round trip
        [2] combobox  Where from?        · San Francisco
        [3] combobox  Where to?          · empty
        [4] textbox   Departure          · empty
  ② 表 + 目标 → 一次 TypeSafe 请求
        operation            （CLICK / TYPE_TEXT / SELECT / SCROLL_UP /
                              SCROLL_DOWN / WAIT / DONE / BLOCKED）
        click_target         （仅当 operation=CLICK 时可执行）
        type_text_target     （仅当 operation=TYPE_TEXT 时可执行）
        select_target        （若存在）
     ★ 每个 target 头只包含"与该操作兼容的元素"
     ★ 两个决策，**一次网络往返**
  ③ 只有 TYPE_TEXT 时才调用一个小 LLM 生成要输入的文本
  ④ Playwright 执行已解析的 DOM 节点
```

**官方给出的确定性收益**（browser-use/jev-ultrafast，MIT，9 天内 9,356 star / 582 fork）：

| 指标 | 结果 | 说明 |
|------|------|------|
| 端到端任务 | **Zürich → London 单程 Google Flights 搜索 7.073 秒** | 含文本生成与页面加载等待 |
| 中位任务耗时 | **9.450 s → 7.092 s（−25%）** | 6 次交替运行、相同模型与设置 |
| 浏览器协议调用 | **1,092 → 101** | 减少约 90% |
| 维基百科导航任务 | 2.798 s | 同一策略，不同任务 |
| 本地酒店搜索/筛选 | 1.896 s | |
| 截图 | **默认回路不含截图** | Jev 消费结构化状态；inspector 才选择性截图 |
| 安全性设计 | 模型输出**永不**变成选择器、坐标、shell 命令或可执行 JS；每个目标都从已观测节点解析；执行前复查页面新鲜度与点击遮挡 | 这条对测试场景很重要 |

**jev-browser（jkudish，另一条路线，更适合测试团队）**：LLM 定目标、Jev 选动作、**Playwright 执行**，以 **MCP server + CLI + library** 三种形态提供。

- MCP 工具：`browser_open` / `browser_do` / `browser_check` / `browser_choose` / `browser_snapshot` / `browser_act` / `browser_screenshot` / `browser_close`
- **结构化状态**（对测试断言极有价值）：`done` / `likely_done` / `needs_login` / `needs_confirmation` / `error` / `stuck` / `max_actions` / `ambiguous` / `blocked`
- **上下文节省**：官方估算中位约 **5 倍** 上下文压缩（8,000 vs 557,000 token），大页面差异最大，小页面无节省
- 声称覆盖：表单、自定义控件、对话框、拖放、上传、iframe、shadow DOM、新标签页、大页面、非英文界面
- **不可逆操作确认门**：出现下单/支付/发送/删除时返回 `needs_confirmation`，必须调用方显式 `allow_irreversible: true` 才继续
- 支持 `JEV_BROWSER_PROFILE` 持久化登录态（**可复用测试账号会话**）

**对 SDET 的四个具体价值点**：

| 价值点 | 说明 |
|--------|------|
| **① 元素定位自愈（self-healing locator）** | 现有做法：XPath/CSS 定位器一改就碎。Jev 做法：把"候选元素表"作为 Choice（≤255 项）让模型按**语义 + 可见文本**选，返回 `choice` + `probabilities` + `confidence`。**置信度高于阈值 → 自动修复定位器并记录；低于阈值 → 告警而非静默通过。** 这是把"自愈"从猜测变成有阈值、可审计的工程行为。 |
| **② 取代快照式 Agent 的 token 与延迟开销** | 主模型不再消费整页快照；决策由 Jev 承担。对 CI 时长敏感的场景，7.1s vs 传统 agent 的分钟级差异是实打实的。 |
| **③ 步骤级结构化断言** | `browser_do` 返回 `likely_done` / `ambiguous` / `stuck` 这类状态，本身就是可断言的枚举值——比"截图比像素"更稳，也比"等 3 秒看有没有报错"更明确。官方明确提醒：**`DONE` 仍需独立结果校验**（不要信模型自评的完成）。 |
| **④ 操作风险门控** | 用一条 Noul 判断"这个操作是否破坏性/不可逆/触达生产"，在 CI 里自动拦住危险步骤。**这正是 jev-guard 类工具在做的事。** |

**UI 场景的边界（必须写进方案文档）**：

| ❌ 不能 / 不可靠 | 依据 |
|-----------------|------|
| 视觉定位、截图断言、像素比对 | 不支持图像输入 |
| 长时程多步任务（目标维持） | 第三方实测 **1/20 vs Luna 17/20** |
| 混乱 DOM / 异步加载 / 弹窗 | 真实网页易击穿 demo 级表现 |
| 部分复杂控件 | jev-ultrafast 明确声明 shadow roots、frames、canvas、上传、弹窗标签页、嵌套滚动、任意键盘控件**都在 MVP 范围外** |
| 计数与排序校验 | jev-browser 的 42 个真实站点任务评估中**仍记录计数与排序校验的失误** |
| 视觉/坐标类操作 | 模型输出永不成为坐标——这是**安全特性**，也意味着不能做坐标点击 |
| 不可逆动作的自动放行 | 设计上要求人工确认 |
| **依赖外部 API（数据出境）** | 核心决策依赖 TypeSafe API + 用户密钥；**注意页面描述、可见文本、甚至可能含凭证的值，都会参与发往外部 API 的决策** → ⚠️ **这一点对内部系统测试是重大合规风险** |

> ⚠️ **给内部项目（如 E9）的现实结论**：Jev 在 UI 自动化上**技术上很合适、合规上不可用**。可以借鉴的是**架构思想**——"抽取元素表 → 用本地小模型/自托管 encoder 做 Choice → 代码执行"这一套，把决策层换成内网可部署的模型即可落地。

### 5.3 场景 B：测试用例生成与回归选择

**先破一个常见误解**：Jev **不能生成测试用例**——它不生成文本。所以"用 Jev 写用例标题、步骤、预期结果"是**路线性错误**。

**但它能渗透到用例生命周期的很多环节**，而且这些环节恰恰是当前最痛的地方：

| 环节 | Jev 原语 | 具体用法 | 价值 |
|------|---------|---------|------|
| **需求 → 用例覆盖度评审** | `Noul` × N | 把需求点逐条拆成 Noul：**"用例 TC-1023 是否覆盖了需求点 R-07？"**（一条需求一个问题，逐条问） | 解决"用例写了但没覆盖需求"的盲区；比让 LLM 通读后打一个分更可靠（官方明确：计数要逐项问 Noul 再在代码里加总） |
| **用例分类与打标** | `Choice` | 把用例分到模块 / 类型（功能、接口、UI、性能）/ 优先级 | 批量治理历史用例库；零样本、规则可随时改 |
| **回归用例选择（核心价值）** | `Noul` | 对每条候选用例问："**本次变更（diff 描述）是否可能影响该用例覆盖的路径？**" 逐条问，代码里汇总成回归子集 | 替代脆弱的路径匹配规则；**能否跑对**取决于你给的 diff 描述质量 |
| **变更性质判定** | `Choice` | 把 SVN diff 归类：新增 / 修改 / 删除 / 重构 / 配置变更 | 零样本、可解释（带概率） |
| **测试数据等价类选择** | `Choice` | 从预定义的边界值/等价类集合中选适用项 | 数据构造前先"选类" |
| **用例质量评分** | `Score` | 按 rubric 给用例的可读性、独立性、可维护性定档（2–10 档） | 注意官方警告：**Score 的数值插值不可靠**，只用它做**阈值判断**，不要用它在两档之间还原精确分 |
| **用例重写（生成）** | ❌ | 用例正文改写、步骤补全 | **必须交给生成式模型**，再用 Jev 校验 |

**最关键的一条工程范式**（MindStudio 实测得出的最强模式）：

```
不要问一个大问题：            "这个需求有没有被覆盖好？"   → 准确率低
而要拆成多个具体指标：        "用例是否引用了需求编号？"
                            "用例的预期结果是否可量化？"
                            "用例是否只验证一个行为？"
                            "用例是否包含前置条件？"
                            ...（逐条 Noul）
然后 → 把结果喂给轻量下游逻辑/分类器做最终判定
实测：单问 ≈ 60% → 拆 8 个具体问题后 → 94%
```

### 5.4 场景 C：缺陷定位、分诊与去重

这是 Jev 在测试领域**性价比最高**的落地场景，因为缺陷流程里天然充满"答案可枚举"的判断。

```
缺陷生命周期中的 Jev 切入点
─────────────────────────────────────────────────────────────────────
① 失败分诊（triage）      pytest 失败信息 → Choice
                          { 环境问题 / 测试数据问题 / 产品缺陷 /
                            用例本身问题 / 依赖抖动 / 超时 }
                          ★ 拆成多条：是否超时？是否断言失败？
                            是否连接失败？错误码是否 5xx？逐条 Noul

② 缺陷去重              两条 bug report → Noul「是否描述同一问题」
                          低成本批量扫描历史缺陷库

③ 严重度 / 优先级评分      Score（按 rubric 定档）
                          注意：只做档位判断，不做数值插值

④ 模块 / 责任人路由        Choice（模块 owner 表）

⑤ 日志分诊               "先给信号打分，再做昂贵的 LLM 分析"
                          —— 已有 jevlogs 类工具：对 OpenTelemetry 日志
                             先评分筛选，再交给 LLM

⑥ 缺陷复现路径相似性       Choice / Score 组合
```

**实测支撑数据**：
- 邮件分诊：300 封邮件分到 15 个部门，**9.9 秒、$0.036**（同期 DeepSeek 只读了 10 封）—— 这个量级可以直接用在**每日失败邮件/告警分诊**上。
- 营销分析流程：扫描 Meta 广告库 → 判断广告格式存活周期 → 评估创意脚本竞争力，原本人工判断**提速 30 倍、成本 < $3**。
- 信息流筛选：读过去三天帖子、提 8 个问题，**约 2 秒、单次 $0.007**。

**缺陷场景的硬边界**：

| ❌ 做不到 | 原因 |
|-----------|------|
| 分析堆栈、追踪调用链 | 多跳推理准确率下降（jaggedness #4） |
| 统计错误出现次数 | 不会计数（#2）—— 日志频次统计必须放代码 |
| 比较时间戳先后、算故障持续时长 | 日期当文本（#3） |
| 读截图复现缺陷 | 不支持图像 |
| 解释"为什么判它是环境问题" | 无 rationale 通道 → **审计/客诉场景必须在上面叠生成模型** |
| 读取用户提交内容做分诊 | 提示注入风险（#6）：**用户可以在 bug 描述里写指令操纵分类** |

### 5.5 场景 D：AI 测试的判分员与守卫

这是与你 AI 测试方向**最贴合**的场景——**用 Jev 测 AI**。

```
被测对象：LLM / Agent 的输出
──────────────────────────────────────────────────────────────────
① 输出断言（LLM-as-a-judge 的低成本替代）
     Noul: "这段回复是否回答了用户的问题？"
     Noul: "这段回复是否包含个人数据？"
     Noul: "这个工具调用是否在授权范围内？"
     Noul: "这条回答是否有依据支撑（相对给定 context）？"
   ⇒ 成本量级：$160 / 百万次评分（vs Fable 5.1 的 $33,000）
   ⇒ 实测与 Fable 5.1 判定一致率 91.5%

② 上下文检索质量（RAG 测试）
     Noul: "该段落是否与问题相关？"（逐段问，代码汇总）
     官方 cookbook 有 RAG passage screening 与 citation check 的现成实现

③ 护栏（guardrail）
     Noul: "这个 prompt 是否是越狱尝试？"
     Noul: "这个工具调用是否超出范围？"
     ⇒ ⚠️ 官方 jaggedness 警告：state 不默认视为敌对，
        所以 ★用 Jev 做的注入过滤器本身可被注入★，上线前必须测

④ 环境/工具调用安全检查
     Noul/Choice: 这条 shell 命令是只读、可逆、还是破坏性的？
     ⇒ jev-guard 类工具正是：先做亚毫秒级本地边界检查，
        再用 Jev 评估爆炸半径、可逆性、破坏潜力

⑤ Agent 轨迹评估
     Noul: "Agent 声称完成了，是否有工具证据支撑？"
     Noul: "是否有人需要查看这条已完成的 agent run？"
```

**这是官方明确列为重点的用例**："Verify everything — 对 LLM 的 prompt、推理轨迹与输出做打分、裁判、护栏、越狱检测。"

**可通过工具**（已在 awesome-jev 目录中出现的形态）：`jev-guard`、`jev-mcp`、`lamma-index-jev`（作为 LlamaIndex 的 reranker/router）、`jev-resilience`（用 Jev 检测"静默 HTTP 200 失败"的语义熔断器）。

> 💡 **`jev-resilience` 这个思路对接口测试特别有启发**：HTTP 200 不等于业务成功。用 Jev 判"响应体是否真的表达了成功"——这是一条 Noul，成本 $0.00004 级。

### 5.6 场景 E：非确定性断言与置信度门控

这是**方法论层面**的贡献，值得单独成节。传统自动化的断言是**二值**的；AI 系统的输出往往**不是二值的**。

```
传统断言：          assert resp.json()["code"] == 0
AI 断言（朴素）：    assert llm_output == expected        ← 必然抖动
AI 断言（Jev 式）：  verdict = jev.noul("该输出是否满足业务规则 X")
                    assert verdict > 阈值              ← 有阈值、可调、可解释

更完整的门控设计：
    confidence < 0.5                 → 不判定，标记"用例无效/环境问题"
    0.5 ≤ confidence < 某风险阈值     → 提交人工复核
    confidence ≥ 某风险阈值           → 自动判定通过/失败
    ★ 阈值必须随风险分级：破坏性动作的自动放行阈值 > 只读动作
    ★ 上线前必须用你自己的标注数据校准阈值，而不是照抄官方 0.9 / 0.7
```

**这里有一个对 SDET 特别重要的测试设计思想**：

> **把"模型的不确定性"当成被测系统的一个可观测属性**，而不是把它当作噪声消掉。
> 也就是：**Jev 的输出信任度本身，是可以被测试的。** 你要测的不只是"它答对了没有"，而是：
> - **校准性**：它说 80% 的时候，真的对 80% 吗？（第三方实测：**不是**，报 80–95% 时实际只有 64%）
> - **稳定性**：同一输入重复调用，答案是否一致？
> - **边界安全性**：会不会对正确答案给出 0 概率？（第三方实测：**6.6% 的情况下会**）
> - **分布外行为**：你内网专有语义上表现如何？
> - **注入抗性**：state 里写指令能否翻转答案？（官方承认**可以**）

**这就是"AI 产品测试"这门岗位真正在做的事**——测概率、测校准、测边界、测分布外，而不是测"对不对"。

### 5.7 场景 F：接口测试与版本影响分析（对应 E9 项目）

你的主线项目是"**SVN 影响分析 → 接口用例实现 → 复测**"三阶段。Jev 的原语与这三个阶段都能对齐，**但有一处合规硬伤**（见文末）。

| 阶段 | Jev 可承担的判断 | 原语 | 说明 |
|------|----------------|------|------|
| **A 分析** | 变更文件 → 变更性质（新增/修改/删除/重构/配置） | Choice | 零样本、规则可改 |
| | 变更 → 影响的业务模块 | Choice（≤255） | 模块表可枚举，正好 255 上限内 |
| | 变更 → 是否影响对外接口契约 | Noul | |
| | 变更 → 是否需要回归、回归范围 | Noul（逐条问） | ★ 比"整包全跑"更省 CI 时间 |
| **B 实现** | 接口字段 → 是否属于边界/异常输入 | Noul × N | 逐字段问，代码汇总 |
| | 用例 → 是否覆盖了该变更点 | Noul | 覆盖度自检 |
| | 用例 → 优先级定档 | Score | 只做档位，不做数值插值 |
| **C 复测** | 失败响应 → 分类（环境/数据/缺陷/用例/抖动） | Choice | 分诊自动化 |
| | 响应体 → 是否业务成功（HTTP 200 陷阱） | Noul | 语义熔断 |
| | 两次运行结果 → 是否是同一失败 | Noul | 抖动识别 |
| | 结果 → 是否需要人工介入 | Noul | 置信度门控 |

**⚠️ 但必须说清楚合规硬伤**：

> 1. **Jev 仅提供托管 API，无自托管方案**，服务部署在美国西海岸。
> 2. 这意味着 **state（可能含内网代码片段、接口字段、业务数据）会出内网、出境**。
> 3. 你的公司明确要求"**代码与数据不出内部网络**"。
>
> **结论：Jev 本身在 E9 项目上不可直接使用。** 可以落地的三条替代路径：
> - **路径 1（推荐）**：借用架构，替换模型——用内网可部署的**自托管 encoder**（ModernBERT / bge 等）实现 Choice/Noul 的等价能力，代码层保留"置信度门控 + 三段式路由"的设计。
> - **路径 2**：**只借用接口约定**——官方开源的 `system-one-adapter-python` 把任意 LLM 包成同一接口。你用内网 LLM 实现同一套 `state + questions → typed answers` 契约，代码可移植、可日后切换。
> - **路径 3**：**只借用方法论**——把"原子化问题 + 在代码里组合 + 置信度三段式路由 + 逐项问再汇总"这套范式，用在现有的内网模型上。**这是零成本、零风险、可立即落地的部分。**

### 5.9 与 pytest 集成的最小可跑示例

以下为**结构示意**（Python 3.10+，需 `pip install typesafe-sdk`）。注意：**这是骨架，阈值必须用你自己的标注数据校准后再上线。**

```python
# conftest.py —— 把"判断"变成 pytest 可用的 fixture
import os
import pytest
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

FAIL_TRIAGE = {
    "env":       "环境/网络/服务不可达，或依赖组件故障",
    "test_data": "测试数据缺失、过期或与前置条件不匹配",
    "product":   "产品代码缺陷导致行为与预期不符",
    "test_case": "用例本身写错（断言错误、步骤遗漏、定位失效）",
    "flaky":     "非确定性抖动（时序、并发、第三方限流）",
    "unknown":   "以上均不符合",           # ★ 必须留逃生出口
}

@pytest.fixture(scope="session")
def jev():
    if not os.getenv("TYPESAFE_API_KEY"):
        pytest.skip("未配置 TYPESAFE_API_KEY，跳过 Jev 相关断言")
    return TypeSafeClient(model="jev-1.13")   # ★ 固定版本，避免阈值漂移


def triage_failure(jev, nodeid: str, error_text: str) -> dict:
    """把 pytest 失败信息分诊为可枚举类别，并返回置信度。

    设计要点（对应 jaggedness 规避）：
      - 拆成多个原子 Noul，而不是一个笼统的 Choice
      - 分类只做语义判断，不做计数/日期比较（那些放代码）
      - 留 unknown 出口，避免"挑最不坏的那个"
    """
    # ★ 先过滤 state（jaggedness #5：无关细节会拉低准确率）
    state = {"nodeid": nodeid, "error": error_text[:2000]}

    resp = jev.system_one(
        state=state,
        questions={
            "is_timeout":  Noul(instructions="错误信息是否表明请求超时或等待超时？"),
            "is_connect":  Noul(instructions="错误信息是否表明连接失败、DNS 失败或服务不可达？"),
            "is_assert":   Noul(instructions="错误信息是否表明断言失败（断言值与期望值不符）？"),
            "is_locator":  Noul(instructions="错误信息是否表明页面元素定位失败或元素不存在？"),
            "is_5xx":      Noul(instructions="错误信息中是否出现了 HTTP 5xx 状态码？"),
            "category":    Choice(
                instructions="根据给出的错误信息，该失败最应归属哪一类？",
                criteria=FAIL_TRIAGE,
            ),
        },
    )

    return {
        "category":   resp.answers["category"].choice,
        "category_conf": resp.answers["category"].confidence,
        "signals": {
            "timeout": resp.answers["is_timeout"].noul,
            "connect": resp.answers["is_connect"].noul,
            "assert":  resp.answers["is_assert"].noul,
            "locator": resp.answers["is_locator"].noul,
            "http5xx": resp.answers["is_5xx"].noul,
        },
    }


# test_xxx.py —— 置信度门控的断言写法
def test_derived_assert_with_gate(jev):
    """演示：把非确定性判断变成有阈值、可复核的断言。"""
    result = triage_failure(jev, "test_login_success",
                            "AssertionError: expected 200, got 401")

    LOW, HIGH = 0.50, 0.85          # ★ 阈值必须自行校准，不要照抄

    if result["category_conf"] < LOW:
        # 模型自己都不确定 → 不要用它来判定用例成败
        pytest.skip(f"分诊置信度过低({result['category_conf']:.2f})，需人工复核")
    elif result["category_conf"] < HIGH:
        # 中置信度 → 记录，但不作为硬结论
        print(f"[需复核] 分诊={result['category']} conf={result['category_conf']:.2f}")
    else:
        assert result["category"] == "product", (
            f"预期归类为产品缺陷，实际 {result['category']} "
            f"(conf={result['category_conf']:.2f}) signals={result['signals']}"
        )
```

**如果要把上面的用例覆盖度检查也加进来**（注意必须**逐条问**，不能问总数）：

```python
def check_requirement_coverage(jev, case_text: str, requirement_points: list[str]) -> dict:
    """逐条需求点问 Noul，再在代码里汇总 —— 这是官方推荐的"计数"做法。"""
    resp = jev.system_one(
        state={"case": case_text[:3000]},
        questions={
            f"r{i}": Noul(instructions=f"该用例是否明确覆盖了以下需求点：{p}")
            for i, p in enumerate(requirement_points)
        },
    )
    covered = [p for i, p in enumerate(requirement_points)
               if resp.answers[f"r{i}"].noul > 0.5]
    return {
        "covered": covered,
        "missing": [p for p in requirement_points if p not in covered],
        # ★ 覆盖率由代码计算，绝不让模型去数
        "coverage": len(covered) / len(requirement_points),
    }
```

**集成时必须记住的四条**：
1. **固定模型版本**（`jev-1.13` 而非 `jev-latest`），否则阈值会随模型升级漂移。
2. **阈值必须自校准**：用你的真实失败样本标注几百条，观察"高置信是否真的更准"，再定线。
3. **先跑影子模式（shadow mode）**：新判断只记录、不阻断，跑一到两周对比人工判定后再启用门控。
4. **不要拿它替代确定性断言**：JSON 字段校验、状态码校验、计数校验，**本来就该用代码做**，而且免费。

## 第六章 面试考点与应答框架

> 面向目标岗位：AI 测试 / AI 自动化测试 / AI 产品测试 / Python 测试开发（成都，17–22K）

### 考点 1：Jev 与 LLM 的本质区别是什么？

**考察点**：是否理解"输出表示形式"背后的工程含义，而不只是背"它更快"。

**答题要点（三层递进）**：
1. **表示层**：LLM 输出字符串（需解析+校验+重试，且可能跑飞）；Jev 输出**类型本身**（Choice/Score/Noul），schema 解析错误在它的运行时里不存在——这是**构造性保证**，不是概率性保证。
2. **采样层**：LLM 自回归、逐 token、串行，成本与延迟随生成长度线性增长；Jev 并行采样，一次产出全部，**加问题几乎不加延迟**。
3. **目标层**：LLM 用 RLHF 优化人类偏好，副产品是**过度自信与模式丢弃**；Jev 用 RLCD 优化**校准**——自报 70% 就该有约 70% 正确。**这一层才是它能进自动化流水线的原因。**

**加分句**："但要注意，**'零幻觉'是结构保证而非语义保证**——它不会给出选项表外的答案，但仍然可能选中错误的选项。官方 CEO 自己承认这一点。"

### 考点 2：Jev 能用在 UI 自动化上吗？

**考察点**：会不会把"AI 能自动化 UI"这个笼统结论直接套上去。

**答题要点**：
- **先否定错误前提**：Jev **不支持图像输入**，所以截图定位、视觉断言、OCR 这条路与它无关——官方连 Doom 演示喂的都是**结构化游戏状态**。
- **再说正确位置**：它是**动作空间决策层**。把页面抽成"编号元素表"，让 Jev 从兼容操作（CLICK/TYPE_TEXT/SELECT/SCROLL/WAIT/DONE/BLOCKED）与兼容目标里做一次 Choice，**两个决策一次网络往返**，然后由 Playwright 执行。只有 TYPE_TEXT 时才叫小 LLM 生成文本。
- **给实测数据**：browser-use/jev-ultrafast 中位任务耗时 9.45s → 7.09s（−25%），浏览器协议调用 1,092 → 101；Google Flights 搜索 7.07s。
- **给边界**：长时程任务实测 **1/20**（对手 17/20）；shadow DOM / frames / canvas / 上传在 MVP 范围外；`DONE` 仍需独立校验。
- **给 SDET 视角**：真正的价值点是**元素定位自愈**——把候选元素表作为 Choice，返回置信度，高置信自动修复、低置信告警。**把"自愈"从猜测变成有阈值的工程行为。**

### 考点 3：能不能用 Jev 生成测试用例？

**考察点**：是否知道"生成"与"判断"是两种不同能力。

**答题要点**：
- **不能生成**——它不生成文本，靠串联 Choice 伪造生成既慢又差（官方 jaggedness 第 9 条明确写了）。
- **但能渗透到用例生命周期的判断环节**：
  - 覆盖度自检：**逐需求点问 Noul**（不要问总数，它不会计数），代码里汇总
  - 回归选择：对每条候选用例问"本次变更是可能影响它覆盖的路径吗"
  - 分类打标、优先级定档、测试数据等价类选择
  - 用例评审：把结果喂给轻量逻辑做最终判定
- **给关键实测**：同一个"钓鱼邮件识别"任务，**问一个大问题只有 62.6%，拆成 8 个具体指标后升到 94%**。→ **结论：问题设计决定结果，拆分是最强的实用模式。**

### 考点 4：用 Jev 做 AI 测试（LLM-as-a-judge）有什么优势与风险？

**考察点**：AI 产品测试岗位的核心能力。

**答题要点**：
- **优势**：成本量级碾压。实测 6,003 条 rubric 检查，与 Claude Fable 5.1 判定**一致率 91.5%**，成本 **$160 vs $33,000**。这个价位意味着**可以对全部流量做监督**，而不是抽样。
- **风险（必须答出，这是区分度）**：
  1. **校准不达标**：第三方 banking77 测试中，**它的 ECE(0.105) 输给了开源 ModernBERT(0.081)**——报 80–95% 置信时实际只有 64% 正确，整体过度自信约 10 个点。**必须做温度缩放之类的后校准**，官方对 MindStudio 的测试也显示温度缩放能降低约 2/3 校准误差。
  2. **"0 概率"是致命失败**：**6.6% 的情况下它对正确标签给出恰好 0 概率**，而开源模型 1,155 次里零次发生。0 概率是**不可恢复**的——没有阈值能救。
  3. **提示注入**：官方明确说 state 不默认视为敌对 → **用 Jev 做的注入过滤器本身可被注入**，上线前必须测。
  4. **不能弃权**：强制二选一时它会挑"最不坏"的，所以**必须自己加 unknown/needs_review 选项**。
  5. **无理由**：没有 rationale 通道，审计和客诉场景必须叠生成模型。
- **加分结论句**："所以它是**过滤器而非裁判**——可以用于筛选'哪些需要人看'，但不能替代人对最终结论的判定。"

### 考点 5：把 Jev 引入你的测试体系前，你会做什么？

**考察点**：是否有工程化的落地方法论（这是"能落地"与"会背概念"的分水岭）。

**答题要点（六步法）**：
1. **挑一个决策**：高频、答案明确、当前由脆弱规则或慢 LLM 承担的那一个（比如失败分诊）。
2. **给错误定价**：写清一次错判的代价 vs 一次慢判的代价。
3. **建测试集**：人工标注几百条真实样本，做"可信答案键"。
4. **设公平基线**：**必须和当前方法、结构化输出 LLM、简单分类器（甚至正则/TF-IDF）一起比。** —— 第三方实测里，一个两行正则拿了 91.8%，TF-IDF 打平了 Jev 的 98.33%。**跳过基线的比较都是营销。**
5. **验校准**：确认"高置信的答案确实更常正确"。不成立就不能用阈值门控。
6. **定上线规则**：auto / review / fallback 三档阈值 + 回滚方案。**并且要算全成本——把人工复核时间算进去；一个便宜但把一半流量甩给人的模型，可能一分钱都没省。**

### 考点 6：Jev 和"结构化输出（JSON mode / function calling）"有什么不同？

**答题要点**：
- JSON mode 是**约束一个生成式模型的格式**；模型仍然以生成式方式推理、以生成式方式计费，**其置信度（若有）反映的是 token 似然，而非结果校准**。
- 而且 schema 只"约束+校验"，生成仍可能在产出合法对象前失败或停止——所以才有"结构化输出错误率 0.58%–45.5%"这组数据。
- Jev 的反命题是：**决策值得拥有一类把"决策"当成训练目标的模型。**
- 工程后果最直观的一条：**你不再需要写几百行 Pydantic/Zod/正则去清洗 markdown 反引号、修截断的括号、对非法枚举值重试。**

## 第七章 结论与决策建议

### 这个模型最值得你带走的三件事

1. **它是一个"位置"，不是一个"更强的模型"。**
   Jev 的意义不在于比 GPT 强，而在于它把「**AI 在软件里该以什么形态存在**」这个问题摆到了台面上：**代码拥有控制流，模型只提供窄判断。** 这个范式与是否使用 Jev 无关，**对任何 AI 测试体系都成立**。

2. **它把"不确定性"变成了可工程化的输入。**
   三段式置信度路由（自动/复核/转人工）、阈值随风险分级——这套设计可以直接搬到任何 AI 系统上。**而"测校准、测边界、测分布外、测注入抗性"正是 AI 产品测试的核心工作内容。**

3. **它的自我披露比它的宣传更值得读。**
   官方那页 `jaggedness` 列了 9 条自己的缺陷（字面理解、不会计数、日期当文本、多跳掉分、context rot、不防注入、指令矛盾、不变量不成立、不能生成）。**"一个厂商愿意公开自己的失败模式"这件事本身，比参数更有信息量。** 反过来，它也让"如何为一个 AI 组件写测试"这件事有了现成的测试用例清单——**那 9 条，就是 9 条测试用例。**

### 给你的具体建议

| 场景 | 建议 |
|------|------|
| **立即可以做（零成本、零风险）** | 把「原子化问题 + 代码里组合 + 置信度三段式路由 + 逐项问再汇总」这套**方法论**用在现有内网模型上。特别是**回归用例选择（逐条 Noul）**与**失败分诊（多 Noul + unknown 出口）**。 |
| **可以试点（注意合规）** | 在**非敏感**场景试用官方 API：AI 输出的判分与护栏（$160/百万次评分这个价位值得验证）。**但先确认数据出境政策。** |
| **不要做** | ❌ 用 Jev 生成测试用例正文；❌ 用 Jev 做算术/计数/日期比较；❌ 用 Jev 做视觉 UI 定位；❌ 在 E9 这类内网项目上直接调用 Jev（数据出境）；❌ 用 `jev-latest` 钉死阈值（版本漂移）。 |
| **架构借鉴** | `system-one-adapter-python` 那套 `state + questions → typed answers` 的**接口契约**值得照抄——你可以在内网实现同一套契约，代码可移植、日后可切换模型。 |
| **面试准备** | 重点准备 [第六章](#第六章-面试考点与应答框架) 的 6 个考点。最有区分度的是**考点 4 的风险清单**与**考点 5 的六步落地法**——能说出"必须设公平基线，正则可能打平前沿模型"的人，比只会背 193.6× 的人高出一个层级。 |

### 一句话总结

> **Jev 不是更聪明的模型，而是把"判断"从"写作"里剥出来的模型。**
> **它的真正贡献是让"AI 的不确定性"变成了一个可以被阈值化、被门控、因而可以被测试的工程对象**——而这，恰恰是测试开发工程师最该擅长的部分。
