一、为什么 SDET 要关注 Pi

对测试开发人员来说，Pi 的价值不在「它能不能写代码」，而在三点：

  1. 它是理解「AI 编码 Agent 分层架构」的最佳样本——Pi 把「核心 harness」「扩展层」「供应商层」拆得最干净，读懂它 = 读懂这一类工具的设计骨架，这是做 AI 测试的地基。
  2. 它天生可编程、可集成——Print/JSON、RPC、SDK 三种非交互模式，让 Agent 能被脚本、pytest、CI 直接驱动，是少见的「开箱即可当测试引擎」的 Agent。
  3. 它把「能力留白」变成测试机会——没有内置权限系统，正意味着权限/安全测试的边界要由你（测试工程师）来定义和验证。
一句话：用 Claude Code / Codex 是「用产品」，用 Pi 是「研究 Agent 怎么被构造、怎么被测」。前者提升效率，后者积累测试能力。

二、快速认知：什么是 Harness

Pi 官方对自己的定义是 minimal terminal coding harness（极简终端编码脚手架），作者是 Armin Ronacher（Flask 作者，GitHub 名 mitsuhiko），MIT 开源。

核心理念：「Adapt pi to your workflows, not the other way around.」——让 pi 适配你的工作流，而不是反过来；无需 fork、无需改内核即可扩展。

2.1 理解「Harness」这个词（面试常考）

「harness」本义是「马具/线束」。在测试领域，test harness（测试脚手架/测试框架）指的是：把被测对象挂起来、驱动它运行、观察它输出的那一层基础设施。Pi 借用了这个思路——它只负责「把模型挂起来、给它最小工具集、驱动它跑」，其余能力全部外置。

2.2 三条核心理念

  • 核心最小化：默认只给模型 4 个工具——read / write / edit / bash。
  • 刻意留白：不内置子代理（sub-agents）、plan mode、权限系统、容器化。想要？自己造或装第三方 package。
  • 可扩展优先：Extension / Skill / Prompt Template / Theme / Package 五层扩展机制完全打开。

2.5 安全与隔离 ⚠️

Pi 默认不内置权限系统，以启动用户权限运行。如需隔离，官方提供三种外部方案：Gondolin micro-VM（工具与 ! 命令路由到本地 Linux micro-VM）、Plain Docker（整个进程跑容器里）、OpenShell（策略控制沙箱）。

⚠️ 对测试工程师的提醒：Pi 的安全边界是「外挂」而非「内置」，意味着权限测试、路径保护、凭据隔离这些测试点需要你自行架设。这与 Codex 的内核级沙箱形成鲜明对比（详见第五节）。

三、Pi 的可测性分析（SDET 核心视角）

「可测性（Testability）」是测试工程师评估任何系统/工具的通用标准。下面用四条可测性维度拆解 Pi 及同类工具。

3.1 可观测性（Observability）

工具可观测能力测试意义
dsh仅追加（append-only）事件日志：消息/工具调用/中间推理/Token 指标/子 Agent 派发全记录，可回放、隔离错误最强，直接支撑「过程追溯」类测试
Codex日志 + 引文 citations + 审批信任档案 .codex/approvals.json可做审批行为分析
Claude Codesession 历史、hooks、auto memory中等
Pipi-telemetry 定义了事件契约 + TUI 展示；事件流可被 Extension 拦截契约清晰但需自行采集

3.2 可控制性（Controllability）

能否从外部精确驱动、注入、断点？

  • Pi：Extension 可拦截 tool_call、注入上下文、自定义 compaction——控制粒度细，适合做「桩/拦截」式测试。
  • dsh：插件即单元，可替换模型/工具/会话/UI，控制面同样强。
  • Codex / Claude Code：以 hooks 为主，控制面相对固定。

3.3 可断言性（Assertability）

输出是否结构化、可解析、可对比？

  • Pi：Print/JSON 与 RPC 输出结构化 JSON/JSONL，可直接被 pytest 断言——这是它作为测试引擎的最大资产。
  • dsh：事件日志为统一结构格式，适合回放与基准对比。

3.4 可隔离性（Isolability）

能否在干净、受限环境中复现？

  • Codex：内核级沙箱（Seatbelt/Landlock），隔离最强。
  • Pi：靠外挂 Gondolin/Docker/OpenShell 实现隔离。
结论：Pi 的「可控制性 + 可断言性」顶尖、可观测性中等、可隔离性靠外部。它最适合的角色是「可编程的测试驱动引擎」，而 dsh 更适合做「过程可追溯的被测对象」。

四、实战：测试工程师怎么用 Pi

场景一：写一个「测试守护」Extension（最推荐入手）

用 TypeScript 给 Pi 注册一个 run_tests 工具，让 Agent 一次调用完成「改代码 → 跑测试 → 拿结构化结果」；同时加权限门控拦截危险命令。

~/.pi/agent/extensions/test-guard.ts

import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { Type } from "typebox";

export default function (pi: ExtensionAPI) {
  // ① 注册"运行测试"工具：Agent 可主动调用，返回结构化结果
  pi.registerTool({
    name: "run_tests",
    label: "Run Tests",
    description: "运行项目测试并返回结构化摘要（通过/失败统计 + 失败用例名）",
    parameters: Type.Object({
      path: Type.Optional(Type.String({ description: "测试文件或目录" })),
    }),
    async execute(toolCallId, params, signal, onUpdate, ctx) {
      onUpdate({ status: "running", message: "正在运行 pytest ..." });
      // 此处调用 pytest/别的测试框架并解析结果（示意）
      const result = { passed: 12, failed: 2, failures: ["test_login", "test_pay"] };
      return {
        content: [{
          type: "text",
          text: `passed: ${result.passed}, failed: ${result.failed}\n${result.failures.join("\n")}`,
        }],
        details: result, // 结构化数据，方便后续断言
      };
    },
  });

  // ② 权限门控：拦截危险 bash 命令（安全测试视角）
  pi.on("tool_call", async (event, ctx) => {
    if (event.toolName === "bash" && event.input?.command?.includes("rm -rf")) {
      const ok = await ctx.ui.confirm("危险操作!", "确认执行 rm -rf?");
      if (!ok) return { block: true, reason: "用户拒绝" };
    }
  });
}

用法：把文件放进 ~/.pi/agent/extensions/，Pi 启动自动发现；或用 pi -e ./test-guard.ts 快速测试。

场景二：用 Print/JSON 模式接入 pytest / CI

Pi 支持无交互的 print / JSON 输出，可在测试脚本中把它当作一个「返回 JSON 的命令」来调用和断言。

test_pi_agent.py（示意）

import json, subprocess

def test_pi_agent_produces_valid_json():
    # 无交互运行一个任务，捕获结构化输出（flag 以官方文档为准）
    out = subprocess.run(
        ["pi", "-p", "--json", "阅读 changes/ 下的变更，跑受影响用例并总结失败原因"],
        capture_output=True, text=True, timeout=120,
    ).stdout
    result = json.loads(out)
    assert "tool_calls" in result          # 存在工具调用轨迹
    assert any("pytest" in str(t) for t in result["tool_calls"])  # 确实跑了测试

CI 里的一行用法（示意）

pi -p "review 这些改动文件的测试覆盖" --json > pi_result.json  # 结果落盘，供后续门槛判断
注：print/JSON 模式的具体 flag（-p / --json）以 官方文档为准，此处为示意。

场景三：把 Pi 当作「被测对象」做 Agent 评测

通用 Agent 评测思路同样适用于 Pi / Claude Code / Codex / dsh，四步走：

1
定义任务集真实编码/测试任务，而非玩具基准
2
注入输入用 JSON/RPC 批量驱动
3
采集轨迹telemetry/事件日志
4
打分断言结果正确性 + 过程合理性

评分维度参考（离线评测 eval 的通用指标）：

维度指标说明
结果正确性任务完成率 / 用例通过率最终产物对不对
过程合理性工具调用是否冗余/越权有没有绕路、有害操作
安全合规危险命令拦截率、越权次数权限边界是否守住
稳定性同任务多次重复的一致性是否幻觉/结果漂移

六、各自优缺点

Pi

优点

  • 极简哲学，学习曲线平滑，符合 Unix 哲学
  • 五层扩展机制，定制灵活到极致
  • 模型中立，近 30 家供应商
  • 四种运行模式，JSON/RPC/SDK 集成能力最强
  • 供应链安全加固，MIT 开源

缺点

  • 不内置权限系统，安全需自行承担
  • 无子代理、无 plan mode
  • 性能不如 Rust 实现
  • 核心留白，对「开箱即用」是负担
Claude Code

优点

  • 代码质量口碑领先（配合 Claude 模型）
  • 生态最成熟（subagents/CLAUDE.md/hooks/MCP/Routines）
  • 全流程闭环，Agentic 体验标杆
  • 企业支持完善（Bedrock/Vertex）

缺点

  • 闭源
  • 深度绑定 Claude 模型
  • token 消耗高（约 Codex 的 3–4 倍）
  • TS 实现，启动和内存偏重
OpenAI Codex

优点

  • 性能最强（Rust 单二进制 8MB）
  • 安全最强（内核级沙箱）
  • 成本最低（token 约为 CC 的 1/3–1/4）
  • 基础设施友好（codex exec / GH Action / CI）
  • 开源，迭代极快

缺点

  • 绑定 GPT（专用 Codex 模型不开放）
  • 真实 bug 修复质量略逊 CC
  • 输出啰嗦，审批日志噪音多
  • 迭代过快，稳定性存疑
DeepSeek Harness (dsh)

优点

  • 微内核 + 一切皆插件，扩展天花板极高
  • 仅追加事件日志，可追溯性最强
  • 社区爆发力惊人（5 天 13.5 万星）
  • 模型中立
  • Hooks 桥复用 CC/Codex 钩子，内置 ACP

缺点

  • 仍处开发者预览（0.1.x），契约可能破坏性变更
  • 插件生态刚起步，长期维护存疑
  • 需配合 DeepSeek 模型效果才好
  • 未经历生产大规模验证

七、测试面试考点（考点 → 考察点 → 答题要点）

Q1：什么是 coding harness？Pi 为什么不叫「编码助手」而叫 harness？

考察点 对 AI 编码 Agent 分层架构的理解，极简 vs 全家桶的工程权衡。

答题要点 harness 是「驱动 + 脚手架」层，只做最小的事（read/write/edit/bash）并开放扩展机制。类比 pytest：核心只负责发现与执行，插件机制才是生态。好处是可审计、可定制、依赖少；代价是能力要靠自己拼装。

Q2：如何对一个 Agent 做「过程可追溯」的测试？（AI 测试核心）

考察点 是否理解 AI 测试「不只测结果，更要测过程」。

答题要点 关键在事件/轨迹采集：dsh 的仅追加事件日志、Pi 的 telemetry 事件契约。记录 tool_call + 中间推理，做到①历史回放 ②错误隔离 ③跨模型基准对比 ④审计合规。落点是「结果正确性 + 过程合理性」双维度评分。

Q3：对一个「无内置权限系统」的 Agent（如 Pi），安全测试怎么做？

考察点 安全边界设计 + 权限测试用例设计。

答题要点 Pi 的安全是外挂（Gondolin/Docker/OpenShell），测试点就在边界上：①危险命令拦截（rm -rf / sudo）②敏感路径保护（.env、node_modules）③凭据隔离 ④越权/逃逸尝试。举例用 Extension 的 tool_call 拦截做门控并验证。

Q4：模型中立 vs 模型绑定，对测试有什么影响？

考察点 模型供应商对测试策略的影响。

答题要点 中立工具（Pi/dsh）可对「同一任务」跨多家模型做 A/B 对比评测，适合横向基准；绑定工具（CC/Codex）有「模型-工具协同优化」红利，质量/速度更优，但难以做纯模型维度的对照实验。测试时要先想清楚测的是「工具」还是「模型」。
